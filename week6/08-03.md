# 오늘 한 것
## presigned url 공격 방어
### 문제 상황
```
아래 시나리오가 가능함

과거에 abc 라는 key를 이용해서 "민증 사진"을 업로드 함
픽업 사진을 업로드 하기 위해, 서버는 def라는 업로드 key를 발금
공격자는 def에 업로드를 안하고, 기존에 abc 키를 이용해서 서버에 픽업 완료 사진 업로드 검증 요청
서버 입장에서는 S3의 abc 키에 이미 사진이 업로드 되어있으니 검증 완료 처리 됨
```

### 1. presigned url의 key에 어떤 목적으로 발급받은 키인지 명시하기
예를 들어, `/uploads/{purpose}/{부르미 id}/filename`의 형식을 바탕으로 purpose에 어떤 목적으로 발급받은 키인지 명시하면 됨
하지만 purpose가 동일한 경우는 막아주지 못함
예를 들어 예전에 발급받은 "배달 완료 인증 사진" 용도의 key를 이번에 진행한 배달건에 대해서 사용한다면 실제로 배달 하지 않고도 이전 key를 사용해서 거짓말 칠 수 있음

### 2. key에 어떤 주문과 엮여있는지 명시하기
주문과 관련된 사진 업로드면 key에 주문 id를 넣으면 됨
예를 들어, `/uploads/{주문id}/{부르미 id}/filename`의 형식을 바탕으로 발급하면 됨
하지만 드리미 인증을 위해 신분증 사진이나 범죄이력조회서 등을 업로드한다면 주문과 관계가 없기 때문에 해당 key 생성 방식을 분기처리 해야 함
```java
public enum UploadPurpose {
    DREAMI_ID_CARD(false),
    DREAMI_CRIMINAL_RECORD(false),
    DELIVERY_CERTIFICATION_IMAGE(true),
    DELIVERY_CERTIFICATION_SIGNATURE(true);
    // ...

    private final boolean requiresResourceScope;
}
```
위처럼 enum에 엮여있어야 할 id를 필요로 하는지 달아두면 지저분하게 분기처리 하지 않고 key 생성 가능

### 3. 업로드 세션 기능
주문 id 등을 넣는다고 해도 이게 같은 주문에 대해서 2번째로 들어온 요청인지 확인할 수 없음
이거 확인하려면 결국 key에 파라미터 하나 더 추가해야 하는데 이렇게 하나씩 추가하다보면 key가 너무 길어지고 패턴이 보임
따라서 DB에 업로드 세션 테이블 하나 선언해서 업로드 시작부터 끝까지 흐름 추적하게 하기
결제에서 원장 쓰는 것처럼

## 정합성
### 낙관적 락
충돌 많이 안 일어날 것 같은데 데이터 읽을 때 락걸지 말자
칼럼에 @Version private Long version;
업데이트할 때 `UPDATE ... WHERE id=? AND version=?` 형태로 버전을 함께 체크
대신 충돌 발생 시 애플리케이션쪽에서 재시도 로직을 직접 작성해야 함

### 비관적 락
충돌이 자주 발생할 것이라고 가정하고 실제 DB 락 걸기

### 조건부 update
```java
Product product = repository.findById(id);  // 1. 읽기
product.setStock(product.getStock() - 1);    // 2. 메모리에서 계산
// 3. flush 시점에 UPDATE (버전 체크 or 락)
```
이런 경우에 코드가 2개의 부분으로 나뉘어 있기 때문에 이 사이에 다른 트랜잭션이 끼어들 수 있음. 이걸 락이나 version으로 막는 것이 낙관적, 비관적 락임

```sql
UPDATE product
SET stock = stock - 1
WHERE id = ? AND stock >= 1
```
update문의 경우 set과 where을 이용해 조회와 수정을 한 쿼리로 해결해서 원자적임

| 상황 | 추천 방식 |
|---|---|
| 단순 증감 연산 (재고 차감, 조회수 증가) + 최고 성능 필요 | **조건부 UPDATE** |
| 수정 전 비즈니스 로직이 복잡함 (여러 필드 검증/계산 필요) | 낙관적/비관적 락 |
| 충돌이 잦고 실패 시 즉시 알아야 함 | 조건부 UPDATE (반환값으로 바로 판단) |
| 트랜잭션 내에서 다른 로직과 얽혀서 재조회가 필요함 | 낙관적/비관적 락 |

### 영속성 컨텍스트
JPA/Hibernate가 엔티티를 관리하기 위해 내부에 두는 1차 캐시 + 변경 감지용 저장소.

```java
Product product = repository.findById(1L).get();
```

이 코드를 실행하면 Hibernate는:
1. DB에서 product를 조회
2. 영속성 컨텍스트(1차 캐시)에 이 엔티티를 저장 (식별자 기준으로 캐싱)
3. 이후 같은 트랜잭션 안에서 `findById(1L)`을 또 호출하면 DB 안 가고 캐시에서 바로 반환
4. 트랜잭션 커밋 시점에 캐시에 있는 엔티티의 변경사항을 감지(dirty checking)해서 UPDATE 실행

### 벌크 연산

`@Modifying` + `@Query`로 작성한 UPDATE/DELETE 쿼리를 말함
- `@Query`: @Query의 JPQL이 SELECT가 아니라 UPDATE/DELETE이면, Spring Data JPA 입장에서는 이걸 그냥 실행할 수가 없음. JPA 스펙상 EntityManager.createQuery()로 만든 쿼리가 executeUpdate()로 실행되어야 하는데, 이건 일반 조회(getResultList())와 다른 실행 경로임
- `@Modifying`: 해당 쿼리는 조회가 아니라 수정 삭제이므로 `executeUpdate()로 실행하라고 Spring Data JPA에게 알려주는 표시임
 

```java
@Modifying
@Query("UPDATE Product p SET p.stock = p.stock - 1 WHERE p.id = :id")
int decreaseStock(@Param("id") Long id);
```
여러 row를 한번에 처리할 수도 있기 때문에 벌크라고 불림

이 쿼리는 영속성 컨텍스트를 완전히 무시하고 DB에 직접 날아감

일반적인 `save()`나 dirty checking은:
```
엔티티 조회 → 영속성 컨텍스트에 반영 → 필드 수정 → flush 시점에 영속성 컨텍스트 보고 UPDATE 생성
```

이지만, 벌크 연산은:
```
JPQL을 그냥 SQL로 변환 → DB에 바로 실행 (영속성 컨텍스트 거치지 않음)
```

이렇게 동작하므로 DB는 바뀌었는데 영속성 컨텍스트(메모리)는 이 사실을 모르게 됨

```java
Product product = repository.findById(1L).get();  
// → 영속성 컨텍스트에 stock=10인 Product가 캐싱됨

repository.decreaseStock(1L);  
// → DB의 실제 stock은 9로 바뀜
// → 하지만 영속성 컨텍스트는 이 사실을 전혀 모름 (벌크 연산은 컨텍스트를 안 건드리니까)

System.out.println(product.getStock());  
// → 10 출력 (실제 DB값 9와 다름 = 데이터 불일치)
```

이 상태에서 `product`를 수정하고 트랜잭션이 끝나면:
```java
product.setName("변경된 이름");
// 트랜잭션 종료 시 dirty checking이 동작해서
// UPDATE product SET stock=10, name='변경된 이름' WHERE id=1
// → stock이 다시 10으로 덮어써짐 (방금 벌크 연산으로 9 만든 게 무효화)
```

벌크 연산으로 DB를 바꿔놨는데, 영속성 컨텍스트에 남아있던 stale(오래된) 값이 나중에 dirty checking으로 다시 DB를 덮어써버리는 상황 발생 가능

따라서 아래처럼 `clearAutomatically = true` 옵션을 사용해서

```java
@Modifying(clearAutomatically = true)
@Query("UPDATE Product p SET p.stock = p.stock - 1 WHERE p.id = :id")
int decreaseStock(@Param("id") Long id);
```

벌크 연산 실행 직후에 영속성 컨텍스트를 비워버리면 됨

```java
repository.decreaseStock(1L);
// 벌크 연산 실행 + 영속성 컨텍스트 clear 자동 수행

Product product = repository.findById(1L).get();
// 캐시가 비어있으니 DB에서 "새로" 다시 조회 → stock=9 (최신값) 정확히 반영됨
```

## 구조만 잘 짜면 무조건 조건부 update가 더 좋은거 아님?
### 수정 전에 복잡한 비즈니스 검증이 필요한 경우
```java
@Transactional
public void applyDiscount(Long orderId, int discountRate) {
    Order order = orderRepository.findById(orderId);
    
    // DB 값만으로는 안 되고, 여러 필드를 조합한 복잡한 판단이 필요
    if (order.getStatus() != OrderStatus.PENDING) {
        throw new IllegalStateException("이미 처리된 주문");
    }
    if (order.getCustomer().getGrade() == Grade.VIP && discountRate > 30) {
        throw new IllegalArgumentException("VIP는 30% 초과 할인 불가");
    }
    if (order.getItems().stream().anyMatch(item -> item.isNonDiscountable())) {
        throw new IllegalStateException("할인 불가 상품 포함");
    }
    
    order.setDiscountRate(discountRate);
    order.recalculateTotal();  // 여러 필드 연쇄 계산
}
```

### 여러 필드를 동시에, 서로 의존적으로 바꿔야 하는 경우
```java
account.setBalance(account.getBalance() - amount);
account.setLastTransactionAt(now());
account.setTransactionCount(account.getTransactionCount() + 1);
account.setStatus(account.getBalance() - amount < 0 ? FROZEN : ACTIVE);
```
필드 하나 값이 다른 필드의 값 결정에 영향을 주는 경우, SQL 한 줄로 표현하려면 CASE WHEN 범벅이 되어서 오히려 가독성 떨어지고 실수하기 쉬움

### 실패 이유를 세분화해서 알아야 하는 경우
조건부 UPDATE는 "0 rows 업데이트됨" 딱 하나의 결과만 알려주기 때문에 세분화해서 사용자에게 알려줄 수가 없음
