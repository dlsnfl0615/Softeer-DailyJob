## JPQL
### YEAR()
날짜 시간 타입 필드에서 연도만 추출함

### constructor expression
JPQL 조회 결과를 엔티티가 아니라 DTO 객첼 바로 매핑해서 반환하는 문법
```java
public record MemberSummaryDto(
    String name,
    String email,
    int birthYear
) {}
---------
@Query("SELECT new com.example.dto.MemberSummaryDto(m.name, m.email, YEAR(m.birthdate)) FROM Member m")
List<MemberSummaryDto> findAllSummary();
```
- Constructor Expression 결과물은 DTO라서 영속 상태가 아님
- dirty checking 대상도 아니고, 그냥 순수한 값 객체(read-only 데이터)로 취급됨
- read-only API에 적합
- import 문 없이 항상 전체 경로(com.example.dto.MemberSummaryDto)를 명시해야 함


## 트랜잭션 (@Transactional)
### 기본 원리

- `@Transactional` 붙이면 메서드 진입 시 트랜잭션 시작, 정상 종료 시 커밋 발생
- 커밋 직전 flush 시점에 영속성 컨텍스트가 관리하는 엔티티의 스냅샷과 현재 상태를 비교
- 변경 감지(dirty checking)되면 `save()`나 `update()` 호출 없이도 자동으로 UPDATE 쿼리 실행 후 DB 반영

### 붙여야 하는 상황

1. 엔티티 조회 후 필드 값을 변경하는 경우
- `findById()` 등으로 영속 상태 엔티티 조회 후 setter로 값 수정
- `@Transactional` 없으면 조회 직후 준영속 상태가 되어 변경사항 DB 반영 안 됨

2. 여러 개의 쓰기 작업을 하나의 단위로 묶어야 하는 경우
- 예: 계좌 이체(출금+입금), 주문 생성+재고 차감
- 중간에 하나라도 실패 시 전체 롤백 필요

3. 여러 테이블에 걸친 연관 데이터 동시 저장/수정
- 부모 엔티티 저장 시 자식 엔티티도 cascade로 함께 저장/수정되는 경우

4. 조회 전용이라도 지연 로딩(LAZY) 컬렉션 접근하는 경우
- 트랜잭션 없으면 `LazyInitializationException` 발생 가능
- 이 경우 `@Transactional(readOnly = true)` 권장 (성능 최적화 + 읽기 전용 명시)

5. 비관적 락(`@Lock`) 사용하는 경우
- 락은 트랜잭션 범위 안에서만 유지되므로 필수

6. 여러 Repository 메서드를 순차 호출하며 하나의 원자적 작업으로 처리해야 하는 경우
- 서비스 레이어에서 여러 저장소 호출을 하나의 트랜잭션으로 묶을 때

### 안 붙여도 되는(붙이면 오히려 손해인) 상황

- 단순 단일 조회만 하고 끝나는 메서드 (지연 로딩 접근 없는 경우)
- 외부 API 호출만 있고 DB 작업이 없는 메서드

## 승인 여부 체크와 저장이 원자적이지 않음
### 문제 상황
| 시각 | 부르미의 `/verification` 요청 (요청 A) | 어드민의 승인 요청 (요청 B) |
|------|----------------------------------------|------------------------------|
| t1 | `dreamiService.assertNotAlreadyApproved()` → "REQUESTED네, 통과" | |
| t2 | | 어드민이 심사 화면에서 이 드리미를 "승인" 버튼 클릭 → `requestCd`를 APPROVED로 UPDATE, commit |
| t3 | `uploadSessionService.checkUpload()` x2 (파일 확인, 시간 좀 걸림) | |
| t4 | `dreamiService.saveVerificationFileKeys()` → `Dreami.create(...)`로 새 엔티티 만들어서 `save()` → `requestCd`가 다시 REQUESTED로, `dreamiAvgScore`도 0으로 덮어써짐 | |

### 그럼 assertNotAlreadyApproved와 saveVerificationFileKeys를 따로 메서드로 합쳐서 거기에 트랜잭션 걸면 되는거 아님?
- MYSQL의 repeatable read
  - 트랜잭션이 시작되고 첫 select를 실행하는 시점에 스냅샷을 만들어서 그 트랜잭션이 끝날 때까지 같은 스냅샷을 계속 재사용함
  - 따라서 이 스냅샷 사이에 어드민이 수정하면 그 값이 없어져버리는 것
- saveVerificationFileKeys에서 먼저 스냅샷이 아닌 최산 상태를 읽어오고 그 값을 기준으로 DB를 변동시켜야 함

### @Lock(LockModeType.PESSIMISTIC_WRITE)
- hibernate가 내부적으로 sql에 for update 붙여서 실행함
