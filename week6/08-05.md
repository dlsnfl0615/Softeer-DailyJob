# 오늘 한 일
## 드리미가 콜 취소했을 때 DB에도 반영이 돼야 함
### 문제 상황
`DreamiService.cancelCurrentDelivery`를 고치던 중, "드리미가 배달을 취소한다"는 같은 동작을 처리하는 엔드포인트가 이미 2개 존재한다는 사실을 발견함.

| | `DeliveryController.cancelByDreami` | `DreamiController.cancelCurrentDelivery` |
|---|---|---|
| 경로 | `POST /api/v1/delivery/orders/{orderId}/cancel/dreami` | `DELETE /api/v1/dreami/deliveries/current` |
| 소유 도메인 | delivery | dreami |
| 프론트 연동 | 이미 연동 완료(`frontend/.../DeliveryTrackScreen.tsx:84`, `api.cancelByDreami(orderId)`) | 아직 연동 안 됨 |
| 파라미터 | `orderId`(path)만, `@LoginUser` 없음 | 없음(로그인 세션의 dreamiId로 "현재 진행 중인 주문"을 서버가 조회) |
| 응답 | `DeliveryStatusResponseDto`(동기 스냅샷) | `void` |
| 실제로 하는 일 | `Delivery.delivery_cd`를 `PICKUP_CANCELLED_BY_DREAMI`로 전이 + 부르미에게 SSE 알림 | 위 작업 + `Orders.releaseFromDreami()` + `matchingService.startMatching()`(재매칭) + `Cancel` 이력 저장 |

### 프론트가 실제로 쓰는 경로엔 재매칭 로직이 아예 없음

"드리미가 이 배달을 취소한다"는 하나의 비즈니스 행위고, 원래 해야 할 일은 (a) `Delivery` 상태 전이,
(b) `Orders`를 다시 매칭 대기로 되돌리기, (c) 재매칭 트리거, (d) 취소 이력 저장 — 이 네 가지가 한
세트.

`DeliveryController.cancelByDreami`는 이 중 (a)의 내용만 존재함

즉 지금 프론트의 "취소" 버튼을 눌러도:
- `Orders.order_cd`는 계속 `IN_PROGRESS`, `dreami_id`도 취소한 드리미로 그대로 남음
- 아무도 재매칭을 트리거하지 않으니 이 주문은 다른 드리미에게 다시 갈 방법이 없음
- 부르미는 배달을 계속 기다리지만 실제로는 아무도 진행하지 않는 상태로 영원히 남음

### `cancelByDreami`엔 소유권 검증이 원래 없었음

`pickupFinishByDreami`/`finishDelivery`는
```java
if (!delivery.getDreamiId().equals(dreamiId)) {
    throw new BusinessException(DeliveryErrorCode.NOT_ASSIGNED_DREAMI);
}
```
를 하는데 `cancelByDreami(UUID orderId)`는 `dreamiId` 파라미터 자체가 없어 이 검증이 없음.
orderId만 알면 그 배달을 맡지 않은 사람도 취소를 걸 수 있는 상태.

### "행 안에서 삭제"로 고치면 안 되는 이유

취소 시 `Delivery` 행을 삭제하는 로직(재매칭 시 같은 `order_id`로 새 행이 또 생겨 `findByOrderId`
단건 전제가 깨지는 걸 막기 위함)을, 두 엔드포인트가 공유하는 `DeliveryService.cancelByDreami` 내부에
넣으면 안 됨. `DeliveryController.cancelByDreami`가 이 메서드를 독립적으로 호출하는 별도 진입점이라,
거기서 호출되면 `Orders`/재매칭 후속 조치 없이 `Delivery` 행만 조용히 사라져서 에러 하나 없이
주문이 영원히 멈춰버리는, 원래 버그보다 더 나쁜 상태가 됨. 그래서 삭제는 `DreamiService.cancelCurrentDelivery`
흐름에만 한정하기로 결정.

## 부르미 쪽은 겹치지 않음 (확인 완료)

`BoormiService.unsubscribeOrder`는
```java
if (!(order.getOrderCd().equals(OrderCd.MATCHING)
        || order.getOrderCd().equals(OrderCd.PENDING_BOORMI_CONFIRMATION))) {
    throw new BusinessException(OrderErrorCode.CANNOT_CANCEL_AFTER_PICKUP);
}
```
로 픽업 시작(`IN_PROGRESS`) 이후엔 취소를 아예 막음. 즉 `unsubscribeOrder`(매칭 전 취소)와
`DeliveryController.cancelByBoormi`(픽업 중 취소)는 서로 다른 주문 상태를 다루는 별개 기능이라
드리미 쪽 같은 진짜 중복은 아님. (다만 `cancelByBoormi` 호출 시 `Orders`가 갱신 안 되는 건 별도의
기존 미해결 갭 — "중복"이 아니라 "아직 안 이어진 것".)

## 향후 작업 방향 후보

| | 프론트 재연동 | 오케스트레이션 위치 | 비고 |
|---|---|---|---|
| A. 완전 이관 — `DreamiController` 엔드포인트로 통일, `DeliveryController.cancelByDreami` 삭제 | 필요 | `DreamiService` | 아키텍처는 가장 깔끔하지만 프론트-백엔드 동시 배포 조율 필요 |
| B. 기존 URL 유지, 내부만 위임 — `DeliveryController.cancelByDreami`가 `DreamiService`의 orderId 기반 오버로드를 호출 | 불필요 | `DreamiService` | URL/응답 타입 그대로라 프론트 안 건드림. 컨트롤러가 다른 도메인 서비스를 호출하는 예외적 구조 발생. `@LoginUser` 추가해 소유권 검증도 같이 고칠 수 있음 |
| C. `DeliveryService` 자체를 확장(Orders/Matching/Cancel까지 직접 의존) | 불필요 | `DeliveryService` | 비권장 — 지금까지 지켜온 도메인 경계(배달 상태 전이만 담당)가 깨짐 |
