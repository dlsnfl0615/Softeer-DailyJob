## @Transactional
### 프록시
- 프록시: 실제 객체를 대신해서 요청 받고 그 앞뒤로 부가 로직을 끼워 넣은 뒤 실제 객체에 위임하는 대리인
- AOP 프록시: Spring이 @Transactional, @Async 같은 애노테이션을 발견하면, 그 Bean을 감싸는 프록시를 자동으로 만들어서 컨테이너에 등록하는 것
  - Spring 컨테이너가 뜰 때 @Transactional이 붙은 Bean을 찾아냄.
  - 그 Bean을 감싸는 프록시 객체를 동적으로 생성. 컨테이너에는 원본 객체가 아니라 이 프록시가 Bean으로 등록됨. 다른 곳에서 @Autowired로 주입받은 건 이 프록시 객체임
  - 프록시의 메서드가 호출되면 실제로 트랜잭션을 시작, 커밋, 롤백하는 Advice 코드가 실행됨
 
### 그냥 원본 객체 등록하면 되지 왜 굳이 프록시로 감쌈?
- 프록시 안 쓰면
  ```java
  public class ServiceA {
    private final PlatformTransactionManager txManager;

    public void methodA() {
        TransactionStatus status = txManager.getTransaction(...);
        try {
            someRepository.save(someEntity); // 진짜 로직은 이 한 줄뿐
            txManager.commit(status);
        } catch (Exception e) {
            txManager.rollback(status);
            throw e;
        }
    }
  }
  ```
  - 핵심 비지니스 로직 코드는 한 줄만 쓰면 되는데 트랜잭션도 고려해야 하니까 위처럼 tray-catch-commit-rollback을 써야 함
  - 진짜 비지니스 관심사와 트랜잭션 처리(횡단 관심사)가 섞이게 됨
 
- 프록시 쓰면
  ```java
  // 원본은 여전히 순수 로직만
  public class ServiceA {
      public void methodA() {
          someRepository.save(someEntity);
      }
  }
  
  // 프록시가 바깥에서 감싸줌 (스프링이 자동 생성)
  public class ServiceA$Proxy extends ServiceA {
      private final ServiceA target;
      private final PlatformTransactionManager txManager;
  
      @Override
      public void methodA() {
          TransactionStatus status = txManager.getTransaction(...);
          try {
              target.methodA(); // 원본 호출
              txManager.commit(status);
          } catch (Exception e) {
              txManager.rollback(status);
              throw e;
          }
      }
  }
  ```
  - 실제로는 ServiceAProxy.methodA()를 호출하게 되지만 이건 스프링이 알아서 해주는 거니까 개발자는 몰라도 됨
  - 이렇게 되면 트랜잭션 처리 등 횡단 관심사를 서비스 클래스마다 직접 안 써도 스프링이 프록시 통해 자동으로 처리해줌

## 커서 방식 vs 페이지 번호 방식
- 페이지 번호 방식: 전체를 N개씩 잘라서 M번째 조각 얻기
- 커서: 결과 집합 안에서 현재 위치를 가리키는 포인터

### 페이지 번호 방식
```sql
-- 3페이지, 페이지당 20개 (1,2페이지를 건너뛰고 세 번째 뭉치)
SELECT * FROM dreami 
ORDER BY created_dtm DESC, id DESC
LIMIT 20 OFFSET 40;
```
- OFFSET 40: 앞의 40개는 무시하고 41번째 부터

### 커서 기반
```sql
-- 마지막으로 본 항목의 created_dtm, id를 커서로 사용
SELECT * FROM dreami 
WHERE (created_dtm, id) < ('2024-06-01 12:00:00', 1053)
ORDER BY created_dtm DESC, id DESC
LIMIT 20;
```
- `WHERE (created_dtm, id) < ('2024-06-01 12:00:00', 1053)`: timestamp를 문자열로써 사전순으로 비교하고 이 시각이 완전히 동일할 경우 id를 기준으로 정렬하라
- 불투명한 문자열: 위 코드에서 `2024-06-01 12:00:00`이 기준값으로 설정되어 이 시각 이전의 20개를 가져오게 되어있음. 하지만 무한 스크롤로 하려면 기준값이 계속 변경되어야 함. 이 기준값을 클라이언트로부터 받아오면 stateless하게 운영할 수 있음. 하지만 클라이언트에게 기준값으로 어떤 속성을 쓰는지 알려주게 되니까 인코딩해서 보내는거임.
  - 어디까지 읽었는지를 인코딩 -> 클라이언트에게 전달 -> 클라이언트는 다시 이 값을 서버에게 돌려줌 -> 서버는 이 값을 기준으로 다시 조회
  - tread safe를 위해, 서버 여러대를 사용하는 경우 서버 인스턴스별로 상태가 갈라지는 문제를 예방하기 위해

### 뭘 써야하는데

| 적합한 방식 | 상황 | 이유 |
| --- | --- | --- |
| 페이지 번호 | 게시판, 관리자 페이지처럼 "N페이지로 바로 점프"가 필요함 | 커서는 순서대로만 이동 가능, 5페이지로 바로 못 감 |
| 페이지 번호 | 전체 개수/전체 페이지 수를 화면에 보여줘야 함 (1 / 234페이지) | 커서는 "전체가 몇 개인지" 자체를 모름, count 쿼리 추가로 필요 |
| 페이지 번호 | 데이터 양이 적당하고(수만 건 이하) 뒷페이지 성능이 크게 문제 안 됨 | 구현이 단순해서 굳이 커서 안 써도 됨 |
| 커서 | 인스타그램/트위터 피드처럼 무한 스크롤 UI | 페이지 번호 개념 자체가 필요 없고, 스크롤할 때마다 다음 것만 계속 가져오면 됨 |
| 커서 | 데이터가 실시간으로 계속 추가/삭제됨 | 오프셋은 그 사이 데이터가 밀리면 중복/누락 발생, 커서는 "이 값 이후"라 안전 |
| 커서 | 데이터 양이 매우 많고(수백만 건 이상) 뒷페이지로 갈수록 성능 저하가 큼 | 오프셋은 앞부분을 다 스캔하고 버려야 해서 느려지만, 커서는 인덱스로 바로 찾아서 항상 빠름 |

## @Modifying(clearAutomatically = true)
### 정의
Spring Data JPA에서 @Query로 직접 작성한 UPDATE/DELETE 벌크 쿼리는 영속성 컨텍스트를 거치지 않고 DB에 직접 실행하므로 영속성 컨텍스트(메모리)에 있는 값이랑 실제 db의 값이 다를 수 있음

clearAutomatically = true 옵션을 주면 벌크 연산 실행 직후 자동으로 `EntityManager.clear()`를 호출

이때 같은 트랜잭션 안에서 관리하고 있던 모든 영속성 컨텍스트들을 다 없애버림

### 문제 상황
```java
private String doPickupFinishByDreami(Delivery delivery, UUID dreamiId, String photoKey) {

  // ...

  // 본인이, 이 주문에 대해, 픽업 인증사진 용도로 발급받은 key인지 확인하고, 업로드 안 됐으면 FILE_NOT_FOUND
  // 여기가 문제!!!!!
  uploadSessionService.checkUpload(UploadPurpose.PICKUP_CERTIFICATION_IMAGE, dreamiId, delivery.getOrderId(),
          photoKey);

  delivery.markDelivering(); // 배달중_정상
  // 비대면 픽업 인증 행 저장 (submittedDtm은 markDelivering이 기록한 pickedUpDtm 재사용)
  pickupCertificationRepository.save(
          PickupCertification.create(photoKey, delivery.getPickedUpDtm(), delivery.getOrderId()));
  alarmBoormiDeliveringBySSE(delivery); // 부르미에게_배달중_상태로_바뀌었다고_전달_SSE사용()
  return "픽업 완료";
}
```
#### 전파 경로

`pickupFinishByDreami`가 `@Transactional`이라 트랜잭션 T1을 열고, 그 안에서 하나의 영속성 컨텍스트(PersistenceContext1, = EntityManager 하나)가 이 메서드 호출 스택 전체에 걸쳐 공유돼. `checkUpload`도 `@Transactional`이지만 기본 propagation이 `REQUIRED`라서, 이미 T1이 열려있으면 새 트랜잭션을 만들지 않고 T1에 그냥 합류

#### 호출 순서
1. `transition()`에서 `deliveryRepository.findByOrderId(orderId)` → `Delivery` D가 PC1에 로드되어 관리 상태가 됨
2. `doPickupFinishByDreami(delivery, ...)` 안에서 `uploadSessionService.checkUpload(...)` 호출 — T1에 합류, 같은 PC1
3. `checkUpload` 내부의 `consume()` → `markConsumedIfIssued()` 실행 → UPDATE 나가고 `clearAutomatically=true`라 `entityManager.clear()`가 PC1 전체에 대해 호출됨
4. 이 `clear()`는 그 쿼리랑 무관하게 PC1에 관리되던 모든 엔티티를 detach시키므로 방금 로드해둔 D도 포함됨
5. `checkUpload` 리턴 후 `delivery.markDelivering()`을 호출하는데, 이때 `delivery`(=D)는 이미 detach된 상태라 Hibernate가 더 이상 추적 안 함

그리고 그 뒤 `alarmBoormiDeliveringBySSE(delivery)`나 `transition()`의 리턴값(`DeliveryStatusResponseDto.from(delivery, message)`)은 메모리상 이미 바뀐 delivery 객체를 그대로 읽어서 응답/SSE를 만들기 때문에, 클라이언트한테 가는 응답이나 알림은 "배달중으로 바뀜"처럼 정상으로 보임. DB에는 반영이 안 됐는데 응답은 성공처럼 보이는 문제
