# 오늘 한 일

## 드리미가 등록된 콜을 조회하지 못함

### 증상
- 드리미가 "시작하기"를 누르지 않으면 화면 진입 시 주변 콜이 전혀 보이지 않음
- "시작하기"를 누른 이후에야 콜이 나타남
- 원래 요구사항("시작하기 여부와 무관하게 화면 진입 시 무조건 노출")과 정반대로 동작

### 원인 위치 — `MatchingService.waitingOrders()`
- `/calls/nearby`는 `waitingOrders()`가 반환한 목록을 거리로 필터링
- `waitingOrders()`는 원래 `OrderOfferGroupStatus.OPEN`인 그룹만 반환
- `OrderOfferGroup`이 OPEN을 유지하려면 주문 생성 시점의 `attemptOfferRound`에서 온라인(MATCHING 상태) 드리미 후보를 최소 1명 발견해야 함
- 후보가 하나도 없으면 `closeForRematch()` 호출 → 그룹이 즉시 `CLOSED`(`rematchRequired=true`)로 전환

#### OrderOfferGroupStatus
- OPEN: 제안 응답 대기중
- MATCHED: 상호 수락 후 매칭된 상태
- CLOSED: 유효한 제안이 없음
  - rematchRequired=true: 후보 드리미가 없어서 오퍼 못 보낸 상태. 나중에 다른 드리미가 등록되면 재시도해야 함
  - rematchRequired=false: 부르미가 취소해서 재시도 대상이 아닌 것

### 전파 경로
1. 부르미 콜 생성 → `MatchingStartRequestedEvent`(AFTER_COMMIT) → 엔진의 `attemptOfferRound` 실행
2. 이 시점 온라인 드리미 부재 → 그룹이 `CLOSED`+`rematchRequired=true`로 전환
3. `waitingOrders()`는 OPEN만 반환 → 닫힌 그룹은 누가 조회하든 `/calls/nearby`에서 배제, 반복 폴링해도 동일
4. 드리미의 "시작하기" 클릭 → `goOnline` → `registerDreami` → `retryRematchWaitingGroups()` 실행 → `rematchRequired=true` 그룹 재오픈 시도 → 그룹이 다시 OPEN으로 전환 → 다음 폴링부터 노출

### 결론
- 프론트 요구사항("시작하기 없이도 콜 노출")과 백엔드 모델("OPEN = 온라인 후보 존재 시에만 유지") 간 정면 충돌
- 프론트는 요구사항대로 구현 완료(진입 시 + 5초 폴링, online 상태 무관) 상태였으나 백엔드가 해당 데이터 자체를 미제공
- 프론트 단독 수정 불가능한 사안

### 적용한 수정
- CLOSED 전체 포함 시 부르미 취소 주문(`cancel()` → `CLOSED`+`rematchRequired=false`, 맵에서 미제거, 영구 잔존)까지 "주변 콜"로 재노출되는 신규 버그 유발
- `rematchRequired` 플래그로 "재매칭 대상 CLOSED"만 정확히 구분해 포함

```java
.filter(group -> group.status() == OrderOfferGroupStatus.OPEN
        || (group.status() == OrderOfferGroupStatus.CLOSED && group.rematchRequired()))
```

- 온라인 드리미 부재 상태로 생성된 콜도 재매칭 대상(`rematchRequired=true`) 상태로 `/calls/nearby`에 노출됨


## 부하테스트
### 툴 비교
#### JMeter
- 장점: 가장 오래되고 검증된 툴, GUI 기반이라 테스트 시나리오 작성이 직관적, 플러그인 생태계 방대(DB, MQ, gRPC 등 거의 모든 프로토콜 지원), 커뮤니티/레퍼런스 자료 압도적으로 많음
- 단점: Java 기반이라 무겁고 메모리 소모가 큼, 동시 사용자 수가 늘어나면 JMeter 실행 서버 자체 리소스가 병목이 됨(스레드 기반이라 vUser 하나당 리소스 소모가 상대적으로 큼), GUI로 만든 스크립트를 CLI/CI에 올리려면 별도 튜닝 필요
- 적합한 상황: 복잡한 시나리오(로그인→여러 API 체이닝→DB 검증 등), 사내에 QA/비개발자도 같이 스크립트를 만들어야 하는 조직, 레거시 프로토콜(SOAP, JDBC 등) 테스트

#### nGrinder
- 장점: 네이버(현 NHN) 오픈소스, 웹 UI로 컨트롤러/에이전트 분리 구조라 대규모 분산 부하 생성이 쉬움, 스크립트는 Groovy/Java 기반이라 개발자 친화적, 결과 리포트가 깔끔하고 실시간 모니터링 UI가 좋음
- 단점: 국내 사용자는 많은데 글로벌 커뮤니티/레퍼런스는 적음, 최신 프로토콜(HTTP/2, gRPC) 지원이 JMeter나 k6 대비 약함, 유지보수 속도가 느린 편
- 적합한 상황: 국내 대기업/스타트업에서 대규모 동시접속 테스트, 에이전트를 여러 대 분산 배치해서 진짜 대량 트래픽을 흉내내야 할 때

#### Locust
- 장점: Python 코드로 시나리오 작성(개발자에게 익숙, 조건문/반복문 등 자유도 높음), Gevent 기반 코루틴이라 스레드보다 가볍게 동시 사용자 시뮬레이션 가능, 웹 UI로 실시간 그래프 확인 용이, 분산 실행(master-worker) 구조가 간단
- 단점: Python GIL/코루틴 특성상 CPU 바운드 작업(암호화, 복잡한 파싱)이 많으면 성능 저하, HTTP 외 프로토콜은 직접 구현해야 함(플러그인 생태계가 JMeter보다 작음)
- 적합한 상황: 개발팀이 직접 스크립트 짜고 관리하는 경우, REST API 중심 서비스, CI/CD 파이프라인에 코드로 관리하고 싶을 때
