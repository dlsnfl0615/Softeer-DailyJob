# 매칭 오퍼 흐름: 1초 배치 → SSE 도착까지 클래스 단위 추적

## 1. 배치 트리거

앱 기동 시(모든 빈이 다 만들어지고 모든 @PostConstruct가 끝나고 등록된 Runner들까지 다 실행되고 난 뒤) `PeriodicMatchingBatchScheduler.start()`(`PeriodicMatchingBatchScheduler.java:27-31`)가
`matchingEngine.scheduleRepeating(new RunMatchingAssignmentCycle(matchingService), matching.batch-interval)`를
한 번만 예약한다(`matching.batch-interval=1s`, `application.properties:150`). 이후 1초마다
`RunMatchingAssignmentCycle.execute()`가 `service.applyRunMatchingAssignmentCycle()` 하나만 호출한다.

## 2. 스냅샷 조립

`MatchingService.applyRunMatchingAssignmentCycle()`(`MatchingService.java:373-379`):

```java
MatchingAssignmentProblem problem = matchingAssignmentProblemAssembler.assemble(
        orderOfferGroups(), reachableWaitingDreamis());
MatchingPlan plan = matchingAssignmentPolicy.createPlan(problem);
matchingPlanApplier.apply(problem, plan, LocalDateTime.now(clock),
        orderOfferGroupsByOrderId, dreamiMap, offersById, offerIdsByDreamiId);
```

- `orderOfferGroups()`(`:151-153`) — 엔진 맵에 있는 `OrderOfferGroup` 전체를 그대로 넘긴다.
- `reachableWaitingDreamis()`(`:117-122`) — `dreamiMap`에서 `status == MATCHING`이고
  `notificationService.isReachableNow(dreamiId)`(= `sseService.isConnected`, SSE 연결이 살아 있는지)를
  통과한 것만 남긴다. **후보 자체가 "SSE로 닿을 수 있는 드리미"로 좁혀진 채 다음 단계로 넘어간다.**

## 3. 후보 쌍 생성 — `MatchingAssignmentProblemAssembler.assemble(orders, dreamis)`

(`MatchingAssignmentProblemAssembler.java:62-121`)

1. `waitingGroups` = 넘어온 그룹 중 `status == WAITING`인 것만, `matchingDreamis` = 입력 그대로(이미 필터링됨).
2. `maxConcurrentOffers`를 `resolveMaxConcurrentOffers(waitingGroups.size(), matchingDreamis.size())`(`:135-140`)로
   **이번 배치 전체에 공통으로 적용될 값 하나**로 계산한다. 기본 `matching.offer-quota-mode=DYNAMIC`이면
   `Math.ceilDiv(dreamiCount, orderCount)`를 `[1, matching.dynamic-quota-max]`로 clamp한다
   (`dynamic-quota-max=5`, `application.properties:153`).
3. `orders`: 각 그룹을 `MatchingOrderInput.from(group, evaluatedAt, maxConcurrentOffers)`로 변환한다.
   `orderWaitingTime = Duration.between(group.matchingStartedAt(), evaluatedAt)`.
4. `dreamis`: `new MatchingDreamiInput(dreamiId, location, Duration.between(dreami.updatedAt(), evaluatedAt))`.
5. 후보 생성 이중 루프(`:91-118`): 주문마다 `OfferScopeResolver.resolve(orderWaitingTime)`로 그 순간 허용되는
   픽업거리(`OfferScope`)를 고르고, `WaitingDreamiGrid`(위경도 0.01° 셀 격자 인덱스)로 그 반경을 덮는 버킷만
   훑어 `geoDistanceCalculator.distanceMeters(...)`(하버사인)로 실거리를 계산한다. **거리가 scope를 넘으면
   그 (주문, 드리미) 쌍은 candidate 자체가 만들어지지 않는다**(`:101-105`). 통과한 쌍마다
   `new MatchingCandidate(orderId, dreamiId, distanceMeters, orderWaitingTime, dreamiWaitingTime, 0, 0, previousInteraction)`을
   만들어 `rawCandidates`에 쌓는다.
6. 마지막에 `matchingAssignmentProblemFactory.create(evaluatedAt, orders, dreamis, rawCandidates)`를 호출한다.

`OfferScopeResolver.resolve`는 `matching.offer-scopes[]`(`application.properties:167-172`)를
`TreeMap<Duration, OfferScope>`로 들고 `floorEntry(orderWaitingTime)`로 "대기시간 이하 중 가장 큰
minOrderWait"를 고른다. 기본값:

| minOrderWait | maxPickupDistanceMeters |
|---|---|
| 0s | 2000 |
| 30s | 3000 |
| 60s | 6000 |

## 4. 적격성(eligibility) 필터

`MatchingAssignmentProblemFactory.create(...)`(`:28-43`)가 `rawCandidates`를
`eligibilityPolicy.isEligible(candidate, evaluatedAt)`로 걸러낸 뒤, `orderCandidateCount`/`dreamiCandidateCount`
(같은 주문/드리미에 몇 명이 경쟁하는지)를 **적격 후보 기준으로 다시 세어 덮어쓴다**(`:45-63`).

기본 구현 `OutcomeCooldownOfferPolicy`(`matching.eligibility-policy=OUTCOME_COOLDOWN`)는 그 (주문, 드리미)
쌍의 `previousInteraction`이 없으면 무조건 적격, 있으면 결과 종류(드리미거절/부르미거절/드리미타임아웃)별
쿨다운(기본 각 10분, `application.properties:157-159`)이 지났는지로 판정한다.

## 5. 점수 계산 — `BalancedScorePolicy.score(candidate)`

`MatchingAssignmentPolicy.createPlan(problem)`의 기본 구현 `ScoreBasedGreedyAssignmentPolicy`(`:46-82`)는
`Comparator.comparingLong(scorePolicy::score)`로 **적격 후보 전체를 하나의 전역 순서로 정렬**한다
(주문별로 따로 정렬하지 않는다 — 한 드리미가 여러 주문의 후보로 동시에 걸릴 수 있어서다).

기본 점수 정책 `BalancedScorePolicy.score`(`policy/scoring/BalancedScorePolicy.java:40-55`):

```java
double distanceRatio = ratio(candidate.distanceMeters(), maxMatchingDistance);
double orderWaitRatio = ratio(candidate.orderWaitingTime().toMillis(), targetOrderWait.toMillis());
double dreamiWaitRatio = ratio(candidate.dreamiWaitingTime().toMillis(), targetDreamiWait.toMillis());

double weighted = weights.distanceWeight() * distanceRatio
        - weights.orderWaitWeight() * orderWaitRatio
        - weights.dreamiWaitWeight() * dreamiWaitRatio;

return Math.round(weighted / weights.totalWeight() * 1000L);
// ratio(value, base) = Math.min(1.0, value / base)  — 0~1로 clamp
```

기본 설정(`application.properties:160-165`): `distance-weight=1`, `order-wait-weight=1`, `dreami-wait-weight=1`,
`max-matching-distance=6000`(m), `target-order-wait=5m`, `target-dreami-wait=5m`.

점수가 **낮을수록**(더 음수일수록) 우선순위가 높다 — 거리가 멀수록 점수가 올라가고, 대기시간이 길수록
(비율이 1에 가까워질수록) 점수가 내려간다.

## 6. 배정 — `ScoreBasedGreedyAssignmentPolicy`

정렬된 후보 목록을 앞에서부터 순회하며(`:64-79`) `consumedDreamiIds`(이미 배정된 드리미)와
`assignedCountByOrderId`(그 주문이 이미 배정한 수, `maxConcurrentOffers` 한도)를 체크해 통과하면
`OfferPolicySnapshot.capture(offerScopeResolver, candidate, evaluatedAt)`로 그 순간의 scope 판단 근거를
그대로 굳혀 `MatchingProposal(orderId, dreamiId, snapshot)`을 만든다. 결과가 `MatchingPlan(proposals)`이다.

## 7. 검증 — `MatchingPlanValidator.validate(problem, plan)`

(`MatchingPlanValidator.java:24-67`) 주문별 제안 수가 `maxConcurrentOffers`를 넘지 않는지, 제안된
(주문, 드리미)가 실제로 `problem.candidates()`에 있고 여전히 적격인지, `snapshot.pickupDistanceMeters()`가
candidate의 실거리와 일치하는지 재확인한다. 하나라도 깨지면 예외를 던져 **아무 상태도 건드리지 않은 채**
이번 사이클을 실패시킨다.

## 8. 적용 + DB 최종 확인 — `MatchingPlanApplier.apply(...)`

(`MatchingPlanApplier.java:56-92`) 검증 통과 후, 그룹이 있고 아직 살아있는 오퍼(`OFFERED` /
`PENDING_BOORMI_CONFIRMATION`)가 없는 주문만 골라 `orderService.findOrders(candidateOrderIds)`로 **DB에서
최신 주문 상태를 한 번에 재조회**한다(스냅샷 조립~적용 사이 다른 트랜잭션이 취소 등을 커밋했을 수 있어서다).
`order_cd != MATCHING`이면 그 주문은 건너뛴다.

## 9. 오퍼 생성

`applyToOrder(...)`(`:94-124`)가 통과한 각 proposal마다 다음을 한다.

1. `new MatchOffer(offerId=UUID.randomUUID(), orderId, dreamiId, OFFERED, appliedAt, snapshot)`를 만들어
   `offersById`/`offerIdsByDreamiId`에 등록.
2. `dreami.markProposed()`로 그 드리미를 `WaitingDreamiStatus.MATCHING → PROPOSED`로 바꾼다(다음 배치의
   `reachableWaitingDreamis()`에서 자동으로 제외됨).
3. `group.addOffersAndOpen(newOffers)`로 방에 오퍼들을 담는다.
4. 오퍼마다:

```java
matchingService.scheduleDreamiOfferTimeout(offer.offerId(), offerTtl);   // 30초 뒤 1회성 만료 액션 예약
notificationService.notify(offer.dreamiId(), MatchingEventType.OFFER_POPUP,
        OfferPopupPayload.from(offer, group.orderSummary(), offerTtl));
```

## 10. SSE 전송까지

`NotificationService.notify(userId, OFFER_POPUP, payload)`(`NotificationService.java:75-83`)가
`NotificationPolicy.PLANS.get("offer_popup")`(`inAppAndWebPush`, `NotificationPolicy.java:18`)을 찾아
`IN_APP`이면 `sseService.send(userId, type, payload)`, `WEB_PUSH`면 별도 스레드풀로 위임한다.

`SseService.send`(`SseService.java:40-43`)는 단일 sender 가상 스레드에
`connectionManager.send(userId, "offer_popup", payload)`를 제출한다(사용자별 이벤트 순서 보존 목적).
`SseConnectionManager.send`(`SseConnectionManager.java:100-111`)가 `activeSessionRegistry.findSseSnapshot(userId)`로
살아있는 연결을 찾아 `emitter.send(SseEmitter.event().name("offer_popup").data(payload))`로 실제 HTTP
청크를 흘려보낸다.

**연결이 이미 끊겼으면**(스냅샷 조립 시점과 이 비동기 전송 시점 사이의 미세한 시간차로 발생 가능)
`sse.events.dropped{reason=not_connected}` 지표만 남기고 **조용히 버려진다** — 재시도·큐잉 없음.
전송 중 예외(죽은 클라이언트)면 `sse.events.dropped{reason=send_failed}`를 남기고 연결을 정리한 뒤
`emitter.completeWithError`한다.

## 구체적 예시

**전제.** 주문 O1이 매칭 시작(`matchingStartedAt = T`)한 뒤 40초가 지난 시점(`evaluatedAt = T+40s`)에
배치가 돈다. O1 픽업지: `(lat 37.5000, lng 127.0300)`. 이 배치 시점에 "MATCHING 상태 + SSE 연결 생존"으로
걸러진 대기 드리미가 3명(D1, D2, D3) 있고, 대기 주문은 O1 하나뿐이다.

| 드리미 | 위치(lat, lng) | O1 기준 하버사인 거리 | 대기 시작~evaluatedAt |
|---|---|---|---|
| D1 | (37.5072, 127.0300) | ≈ 801m | 20초 전 |
| D2 | (37.5225, 127.0300) | ≈ 2,502m | 300초(5분) 전 |
| D3 | (37.5360, 127.0300) | ≈ 4,003m | 10초 전 |

(경도가 같아 `h = sin²(Δlat/2)`로 단순화되는 하버사인 공식을 그대로 손계산한 값이다.)

**① 동시 오퍼 한도.** `matching.offer-quota-mode=DYNAMIC`, 주문 수=1, 드리미 수=3 →
`ceilDiv(3,1)=3` → `[1,5]`로 clamp → **maxConcurrentOffers=3**.

**② scope 판정.** `orderWaitingTime=40s`. `matching.offer-scopes`는 `{0s→2000m, 30s→3000m, 60s→6000m}`.
`floorEntry(40s)` = `30s` 키 → **maxPickupDistanceMeters=3000m**.

**③ 후보 생성(Assembler).** D1(801m), D2(2,502m)은 3000m 이내 → candidate 생성. **D3(4,003m)은 3000m를
넘어 아예 candidate가 만들어지지 않는다**. previousInteraction은 셋 다 없다고 가정한다.

**④ 적격성.** D1, D2 모두 `previousInteraction.isEmpty()` → 즉시 적격.

**⑤ 점수 계산.** (`maxMatchingDistance=6000m`, `targetOrderWait=targetDreamiWait=300s`, 가중치 1:1:1)

- 공통: `orderWaitRatio = min(1, 40/300) = 0.1333`
- D1: `distanceRatio = 801/6000 = 0.1335`, `dreamiWaitRatio = min(1, 20/300) = 0.0667`
  `weighted = 0.1335 - 0.1333 - 0.0667 = -0.0665` → `score = round(-0.0665/3*1000) = **-22**`
- D2: `distanceRatio = 2502/6000 = 0.4170`, `dreamiWaitRatio = min(1, 300/300) = 1.0000`
  `weighted = 0.4170 - 0.1333 - 1.0000 = -0.7163` → `score = round(-0.7163/3*1000) = **-239**`

**⑥ 정렬/배정.** 점수 오름차순(낮을수록 우선): D2(-239) → D1(-22). 둘 다 `maxConcurrentOffers=3`을
넘지 않으므로 **둘 다 배정된다** — 5분을 기다린 D2가 800m 더 가까운 D1보다 거리 손해를 감수하고도 먼저
뽑힌 것이 대기시간 가중치의 효과다. (만약 quota가 1이었다면 D2만 뽑히고 D1은 이번 라운드에서 탈락,
다음 배치에서 dreamiWaitingTime이 늘어난 채 재시도된다.)

**⑦ 검증 + DB 재확인.** `MatchingPlanValidator`가 두 제안 모두 통과시킨다. `orderService.findOrders([O1])`이
여전히 `MATCHING`임을 재확인한다.

**⑧ 오퍼 생성 및 SSE 발송.** D2에게 `offerId=E1`, D1에게 `offerId=E2`(둘 다 `status=OFFERED`,
`statusUpdatedAt = T+40.0s`)가 만들어지고, 각각 `matchingEngine.schedule(ExpireDreamiOffer, 30s)`가
걸린다(만료 시각 `T+70.0s`). D2에게 나가는 `OfferPopupPayload`는 다음과 같은 값을 담는다.

```
offerId=E1, orderId=O1
offeredAt = T+40.0s, expiresAt = T+70.0s
offerPolicy = { scopeKey=30s, evaluatedAt=T+40.0s, orderWaitingSeconds=40,
                pickupDistanceMeters=2502, maxPickupDistanceMeters=3000 }
deliveryAmount / itemName / originAlias / destinationAlias 등 = O1의 OrderSummaryDto 스냅샷
```

이 payload가 `notificationService.notify(D2, OFFER_POPUP, payload)` → `sseService.send` →
`SseConnectionManager.send`를 거쳐, D2의 브라우저에 열려 있는 `EventSource`로 `event: offer_popup`
프레임 하나로 도착한다. 같은 일이 D1에게도 각자의 snapshot(`pickupDistanceMeters=801`)으로 독립적으로
일어난다.

**D3는 애초에 candidate가 아니었으므로 이번 라운드에서는 아무 이벤트도 받지 않는다.** 다음 배치
(`T+41s`)에서 O1의 `orderWaitingTime`이 41초가 돼도 여전히 30~60초 구간(3000m)이라 D3는 계속 제외되고,
`orderWaitingTime ≥ 60s`가 되어야 scope가 6000m로 넓어져 처음으로 candidate가 된다.

## 1. 로그인

1. `LoginCheckInterceptor.preHandle`이 `@PublicApi`가 없는 모든 `/api/**` 요청마다 세션을 검사합니다. 단순히 `LOGIN_USER`가 세션에 있는지만 보는 게 아니라, `ActiveSessionRegistry.isCurrent(userId, sessionId)`로 "이 세션이 지금도 이 계정의 유일한 활성 세션인가"까지 확인합니다. 다른 기기에서 재로그인하면 이전 세션은 만료 전이라도 즉시 막힙니다.
2. `POST /api/v1/user/login` → `loginQueue.submit(request)`로 로그인 요청 몰림을 대기열로 흡수한 뒤, `LoginSession.create()`가 새 세션을 발급하고(기존 세션은 invalidate — 세션 고정 공격 방지) `activeSessionRegistry.replace(...)`로 활성 세션을 교체합니다. 이전 세션이 SSE 연결을 들고 있었다면 이 시점에 `SseCloseReason.REPLACED_BY_LOGIN`으로 끊깁니다. 프론트는 로그인 성공 응답으로 `sessionStore.login()`이 `isAuthenticated: true`를 반영합니다. 이어서 `/me`를 호출해 `UserDto`(`isDreami`, `activeRole`, `activeOrderCd` 등)를 받고, `resolveLandingRoute()`가 이 값으로 "진행 중 배달이 있으면 추적 화면, 드리미인데 진행 주문이 없으면 매칭 화면, 그 외 홈"으로 라우팅을 결정합니다.
3. **SSE 연결이 이 시점부터 열립니다.** `isAuthenticated && userId`가 true가 되는 순간 `SseTabCoordinator`가 Web Lock으로 대표 탭을 뽑고, 그 탭만 `new EventSource(".../api/v1/sse/subscribe", {withCredentials:true})`를 엽니다. 서버의 `SseController.subscribe` → `SseService.subscribe(userId, sessionId)`가 emitter를 만들고 최초 `connected` 이벤트를 내려보내야 클라이언트 상태가 `connected`로 바뀝니다. 이 전환 시점에 `matching.stopMatchingPolling()` + `syncCurrentMatching()` + `refreshUser()`가 실행되는데, 이는 **로그인 직후 SSE가 완전히 맺어지기 전까지는 폴링으로 매칭 상태를 메꾸는 구간이 존재**한다는 뜻입니다.

## 2. 부르미가 등록 (주문 등록)

### MatchingEngine.queue에 매칭 시작 액션 등록

부르미가 주문을 등록하면 `OrderPlacementService.place`가 한 트랜잭션에서 `Orders.create(...)`(초기 상태 `MATCHING`)와 포인트 결제(`paymentService.payWithPoint`)를 처리합니다. 결제가 실패하면 주문 저장도 함께 롤백됩니다. 트랜잭션 안에서는 `MatchingStartRequestedEvent`만 발행하고, `MatchingEngine`에는 아직 아무것도 들어가지 않습니다.

`MatchingService.onMatchingStartRequested`가 `@TransactionalEventListener(phase = AFTER_COMMIT)`로 걸려 있어, **주문 커밋이 끝난 뒤에야** `matchingEngine.submit(new StartMatching(...))`으로 큐에 들어갑니다(커밋 전에 넣으면 드리미가 아직 DB에 없는 주문을 조회하는 레이스가 생기기 때문). 엔진 워커가 이 액션을 실행하면 `OrderOfferGroup`(방)만 만들어지고, 이 단계에서 특정 드리미에게 오퍼가 나가는 건 아닙니다 — 오퍼 발송은 4번의 1초 주기 배치가 담당합니다.

이 단계에서 부르미에게 별도 SSE 알림은 없습니다. `place()`의 반환값(`orderId`)이 REST 응답으로 바로 돌아가며, 부르미가 처음 SSE 알림을 받는 건 5번(드리미 수락 시 `dreami_info`)입니다.

## 3. 드리미가 온라인

### MatchingEngine.queue에 드리미 온라인 등록 액션 제출

드리미가 온라인 전환을 누르면 `POST /api/v1/dreami/status/online` → `DreamiService.goOnline(dreamiId, location)`이 승인 상태와 "지금 진행 중인 주문이 없는지"만 DB로 확인(읽기 전용 트랜잭션)한 뒤 `matchingService.registerDreami(dreamiId, location)`을 호출합니다.

`registerDreami`는 호출 스레드에서 중복 등록만 빠르게 걸러내고, 실제로는 `matchingEngine.submit(new DreamiRegister(...))`으로 큐에 넣습니다. 엔진 워커가 이를 실행해야 `dreamiMap`(엔진 스레드 전용 인메모리 맵)에 `WaitingDreami`가 들어갑니다 — **DB에는 이 "온라인 대기" 상태가 전혀 남지 않아서**, 서버가 재시작하면 이 등록은 사라지고 실제로도 오프라인이 맞는 상태가 됩니다.

**"온라인 등록"과 "위치 브로드캐스트"는 서로 다른 메커니즘입니다.** `DreamiOfflineDetector`는 온라인 등록의 반대짝이 아니라, **배달이 시작된 이후 단계**에서 `@Scheduled(fixedDelayString = "${delivery.dreami-offline-scan-interval}")`로 주기 스캔하며 드리미 GPS 위치 전송이 끊겼는지(30초 무소식 → 인앱+웹푸시, 3분 무소식 → SMS)를 판정하는 별개 기능입니다(8번 참고). 대응하는 프론트 훅 `useDreamiLocationBroadcast`도 `orderId`가 있을 때(즉 매칭이 끝나 배달 중일 때)만 동작하며, GPS 좌표를 최초 즉시 1회 + 이후 **5초 간격 폴링**으로 `POST .../dreami-location`에 전송합니다.

## 5. 드리미가 수락

### Orders 테이블에 order_cd 상태 변경

`DreamiService.acceptOffer()`가 `@Lock(PESSIMISTIC_WRITE)`로 주문을 잠금 조회해 `MATCHING` 상태를 재확인한 뒤 `order.markPendingBoormiConfirmation(dreamiId, offerId)`로 `PENDING_BOORMI_CONFIRMATION`으로 전이시키고, 커밋과 함께 `DreamiAcceptedEvent`를 발행합니다.

### 부르미에게 확인 요청이 전달되는 경로 (SSE)

`MatchingService.onDreamiAccepted`가 `AFTER_COMMIT`로 이 이벤트를 받아 엔진 큐에 `AcceptByDreami` 액션을 제출합니다(왜 커밋 후인가 — 부르미의 최종 확정은 DB의 `order_cd`가 `PENDING_BOORMI_CONFIRMATION`인지 검사하므로, 커밋 전에 제출하면 아직 반영 안 된 상태를 보고 확정이 실패할 수 있음). 엔진 워커의 `applyAcceptByDreami`는 두 갈래로 나뉩니다.

- 수락한 드리미: 부르미 응답 타임아웃(30초)을 걸고(`ExpireBoormiOffer`), **부르미에게 `DREAMI_INFO`(수락한 드리미 정보 + 예상 픽업 시간 + 응답 마감 시각)를 SSE로 전송**(`inAppAndWebPush`).
- 같은 방의 나머지 대기 드리미들: 오퍼를 회수하고 다시 매칭 대기시키며, **`OFFER_CLOSED`("선착순 마감")를 SSE로 전송**(`inAppOnly`).

부르미의 30초 응답 타임아웃도 같은 방식으로 걸리며, 실행 시점에 DB 락을 다시 확보해 이미 부르미가 확정/거절해버린 경합 패배 케이스는 조용히 무시합니다.

## 6. 부르미가 수락

### Orders 테이블에 order_cd 상태 변경

`BoormiService.confirmDreami`가 같은 비관적 락 경로로 주문 소유자·상태·offerId를 검증한 뒤 `order.confirmDreami(dreamiId)`로 **`order_cd`를 `IN_PROGRESS`로 전이**시킵니다. **이 시점에는 아직 `Delivery` 엔티티가 없습니다.** 커밋과 함께 `BoormiConfirmedEvent`만 발행됩니다.

### 드리미에게 확정 알림이 전달되는 경로 (SSE) — 배달 시작과 한 액션으로 이어짐

`MatchingService.onBoormiConfirmed`(`AFTER_COMMIT`)가 엔진에 `AcceptByBoormi`를 제출합니다. 엔진 워커는 이 하나의 액션 안에서 매칭을 확정 처리한 뒤 **곧바로 `deliveryService.startDelivery(...)`를 호출**합니다 — 즉 "부르미 수락"과 "배달 시작"은 코드 상으로는 같은 액션에서 연속 실행됩니다. **드리미 본인에게 "확정됐다"는 별도 이벤트는 없고**, 7번에서 다루는 `delivery_started_dreami` SSE 알림이 곧 그 확정 통지 역할을 합니다.

### 부르미가 거절하는 경우

`BoormiService.rejectDreami`가 같은 락 경로로 `order.rejectDreami()`를 호출해 **`order_cd`를 다시 `MATCHING`으로, `dreami_id`를 비웁니다.** 커밋 후 거절당한 드리미에게 **`BOORMI_REJECTED` SSE**(`inAppOnly`)를 보내고 다시 매칭 대기시킵니다. 별도의 "재오퍼 트리거"는 없고, 4번의 1초 배치가 다음 회차에 자동으로 재평가합니다.

## 7. 배달 시작

### 순서: Orders가 먼저 IN_PROGRESS로, Delivery는 그다음 별도 트랜잭션에서 생성

`Orders.IN_PROGRESS` 전이(6번)와 `Delivery` 생성(`DeliveryService.startDelivery`)은 **서로 다른 트랜잭션**입니다. 그 사이 시간차 때문에 `Delivery` 생성이 실패하면 `Orders`는 이미 `IN_PROGRESS`인데 `Delivery` 행이 없는 상태로 고착될 수 있습니다(관련 위키: "매칭 확정 후 Delivery 생성 실패로 Orders가 IN_PROGRESS에 고착되는 문제").

```java
@Transactional
public void startDelivery(UUID orderId, UUID dreamiId, UUID boormiId) {
    Orders order = orderService.getOrder(orderId);
    if (order.getOrderCd() != OrderCd.IN_PROGRESS) {
        throw new BusinessException(DeliveryErrorCode.DELIVERY_START_NOT_ALLOWED);
    }
    if (!dreamiActivationChecker.isActivatedDreami(dreamiId)) {
        throw new BusinessException(DeliveryErrorCode.DREAMI_NOT_ACTIVATED);
    }
    Delivery delivery = deliveryRepository.save(Delivery.create(orderId, dreamiId, boormiId));
    alarmBoormiDeliveryStartedBySSE(delivery);
    alarmDreamiDeliveryStartedBySSE(delivery);
}
```

### 알림: SSE + 웹푸시로 양쪽에 동시 전달

`DELIVERY_STARTED_BOORMI`/`DELIVERY_STARTED_DREAMI` 이벤트가 `DeliveryNotificationEvent`로 발행되고, 트랜잭션이 커밋된 뒤(`AFTER_COMMIT`)에만 실제 전송됩니다. 둘 다 `inAppAndWebPush`라 앱을 안 보고 있어도 잠금화면 알림이 뜹니다.

## 8. 드리미가 픽업 완료

### 픽업 완료 처리

`pickupFinishByDreami`는 상태가 `PICKUP_NORMAL`/`PICKUP_DELAYED`일 때만 허용되며, `uploadSessionService.checkUpload(...)`로 드리미 본인이 발급받은 픽업 인증사진이 실제로 업로드됐는지 확인한 뒤 `delivery.markDelivering()`(`DELIVERING`)으로 전이하고 인증 정보(`PickupCertification`)를 저장합니다.

`checkUpload`가 쓰는 `markConsumedIfIssued`(조건부 UPDATE)는 현재 `clearAutomatically`를 켜지 않아 안전한 상태입니다. 이전 대화에서 다룬 "영속성 컨텍스트 우회로 다른 엔티티가 조용히 detach되는" 사고와 같은 계열의 위험이 구조적으로 존재하는 지점이지만, 지금은 회귀 테스트(`UploadSessionRepositoryIntegrationTest`)로 이 전제가 지켜지고 있습니다.

### 알림: 부르미에게 SSE + 웹푸시

`DELIVERY_DELIVERING`("픽업이 완료됐어요")이 `inAppAndWebPush`로 전송됩니다.

## 9. 드리미가 배달 완료

### 배달 완료 처리와 Orders → COMPLETED

`DELIVERING` 상태에서만 허용되며, 배달완료 인증사진을 검증한 뒤 `delivery.markDelivered()`(`DELIVERED`)와 `orderService.complete(orderId)`(**`Orders.order_cd → COMPLETED`**)를 같은 트랜잭션에서 처리합니다.

### 정산: 배달 완료가 지급 확정 트리거

같은 트랜잭션에서 `paymentService.settleOrder(orderId, dreamiId)`가 호출됩니다. 부르미의 포인트는 주문 시점에 이미 차감돼 `PENDING` 상태로 남아 있다가, 이 호출로 `PAID`로 확정되고 동시에 드리미의 `MoneyWallet`에 같은 금액이 적립됩니다. 즉 "배달이 끝나야 드리미에게 돈이 실제로 지급 확정된다"는 정책이 이 한 지점에 구현돼 있습니다.

### 알림: 부르미에게 SSE + 웹푸시

`DELIVERY_COMPLETED`("배달이 완료됐어요")가 물품명과 함께 전송됩니다. 프론트는 이 이벤트를 받으면 완료 안내를 2초 보여준 뒤 리뷰 화면으로 자동 이동시킵니다.

## 10. 평가하기

### 완료된 주문에 대한 상호 별점 (`ReviewService.writeScore`)

부르미와 드리미가 같은 메서드를 호출하고, 로그인한 사용자가 이 주문의 어느 쪽인지에 따라 저장 테이블이 갈립니다(부르미가 평가 → 드리미에게 남기는 `DreamiReview`, 반대도 동일). 주문이 `COMPLETED`가 아니거나 이미 리뷰를 남겼으면 거부됩니다. 별점을 먼저 남겨야 하고, 텍스트 내용은 나중에 채우거나 수정할 수 있습니다.

### 평균 평점 갱신 — 매칭 스코어링에는 반영되지 않음

리뷰가 저장될 때마다 상대방의 전체 리뷰 평균(`avgScore`)이 갱신되어 배달 완료 화면에 노출됩니다. 다만 매칭 스코어링 정책들(`scoring/*ScorePolicy`) 어디에도 `avgScore`를 참조하는 코드가 없어, **현재 평점은 매칭 우선순위에는 반영되지 않고 화면 표시용으로만 쓰입니다.**

### 알림 없음

`ReviewService`에는 SSE/웹푸시/이벤트 발행 코드가 전혀 없습니다. 평가하기는 이 전체 흐름에서 SSE·폴링 어느 것도 타지 않는 유일한 단계입니다.
