## 외부 api 호출 타임아웃
### java.net.http.HttpClient
실제 커넥션을 맺고 http 요청 응답 주고받는 순수 자바 표준 api
```java
HttpClient httpClient = HttpClient.newBuilder()
  .connectTimeout(CONNECT_TIMEOUT)
  .build();
```
### org.springframework.http.client.JdkClientHttpRequestFactory

#### ClientHttpRequestFactory

`RestClient`(또는 예전의 `RestTemplate`)는 "HTTP 요청을 어떻게 만들지, 어떤 라이브러리로 실제 통신을 할지"를 스스로 알지 못하므로 대신 이 인터페이스에 위임. Spring은 이 인터페이스의 구현체를 여러 개 제공

| 구현체                                   | 내부적으로 쓰는 라이브러리                    |
| ---------------------------------------- | --------------------------------------------- |
| `SimpleClientHttpRequestFactory`         | `java.net.HttpURLConnection` (구식)           |
| `HttpComponentsClientHttpRequestFactory` | Apache HttpClient5                            |
| `JettyClientHttpRequestFactory`          | Jetty Client                                  |
| `JdkClientHttpRequestFactory`        | `java.net.http.HttpClient` (JDK 11+ 표준) |

`RestClient.builder().build()`처럼 아무것도 지정하지 않으면, Spring이 classpath를 훑어서 Apache HttpClient5나 Jetty가 있으면 그걸 쓰고, 없으면 마지막 fallback으로 이 `JdkClientHttpRequestFactory`를 자동으로 고름. 이 프로젝트는 build.gradle에 그런 외부 HTTP 클라이언트 의존성이 없으면 이 클래스를 사용하게 됨.

```java
HttpClient httpClient = HttpClient.newBuilder()
        .connectTimeout(CONNECT_TIMEOUT)   // ① 여기서만 connect timeout 설정 가능
        .build();
JdkClientHttpRequestFactory requestFactory = new JdkClientHttpRequestFactory(httpClient); // ② 그 클라이언트를 Spring 어댑터로 감싸기
requestFactory.setReadTimeout(READ_TIMEOUT); // ③ read timeout은 이 어댑터 쪽에서 설정
```

- ①은 순수 JDK API — "연결을 맺는 데 3초 넘게 걸리면 포기"
- ②는 그 JDK 클라이언트를 Spring이 이해하는 형태로 감싸는 어댑터 객체를 만드는 것
- ③은 Spring 쪽 API — "요청을 보내고 응답이 5초 안에 안 오면 포기"

- 실제 호출 흐름

  - `restClient.get().uri(uri).retrieve()...`를 호출하면, `RestClient`는 내부적으로 `requestFactory.createRequest(uri, httpMethod)`를 호출해 `JdkClientHttpRequest` 객체를 하나 만듦
  - 그 객체가 생성자로 받은 `httpClient`/`readTimeout`을 이용해 실제 요청을 실행. 즉 `RestClient` 쪽 코드(`getCoordinates()` 메서드)는 하나도 안 바뀌었고, 요청을 만드는 공장만 "타임아웃 없는 기본 설정"에서 "타임아웃 있는 설정"으로 교체한 셈입니다.
 
### 그럼 Apache HttpClient5나 Jetty는 이거랑 비교해서 뭐가 다름?
`RestClient`가 실제로 무엇을 통해 통신하느냐의 차이인데, 셋 다 블로킹 방식으로 요청 보냄. 차이는 커넥션 풀 관리 수준, 부가 기능, 의존성 무게에서 갈림

|                 | JDK `HttpClient` (현재 씀)                | Apache HttpClient5                                                                                                     | Jetty Client                                                           |
| --------------- | --------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 의존성          | 없음 (JDK 11+ 내장)                           | `httpclient5` 별도 추가 필요                                                                                               | `jetty-client` 별도 추가 필요                                              |
| 커넥션 풀       | 있지만 단순함, 세부 튜닝 옵션 거의 없음       | `PoolingHttpClientConnectionManager` — 라우트(호스트)별 최대 커넥션 수, TTL, 유휴 커넥션 정리 스레드 등 세밀하게 튜닝 가능 | Jetty 서버와 같은 비동기 IO 엔진 공유, 튜닝 가능하지만 생태계가 Jetty 전용 |
| 재시도/인터셉터 | 없음 (직접 구현해야 함)                       | `HttpRequestRetryStrategy`, 요청/응답 인터셉터 등 성숙한 확장점 제공                                                       | 있지만 Apache만큼 널리 쓰이는 패턴이 없음                                  |
| 타임아웃 모델   | connect / 요청 전체(request) 타임아웃 — 2가지 | connect / 커넥션 풀에서 커넥션 대여 대기(connectionRequestTimeout) / socket(응답) — 3가지로 더 세분화                  | 유사하게 세분화 가능                                                       |
| HTTP/2          | 기본 지원 (TLS ALPN 협상)                     | 지원하지만 부가 모듈(httpclient5-h2) 필요, JDK만큼 매끄럽진 않음                                                           | 매우 강함 — Java 진영에서 HTTP/2를 가장 먼저 구현한 축                     |
| 성숙도/생태계   | 상대적으로 신생 (Java 11, 2018~)              | 오래되고 검증됨, 사실상 업계 표준                                                                                          | Jetty 서버 쓰는 프로젝트에서 자연스럽게 선택                               |

- 언제 뭘 쓰는 게 나은가

  - JDK `HttpClient`: 호출 대상이 카카오 API 하나처럼 단순하고 외부 연동 지점이 적을 때 적합. 의존성 추가 없이 표준 라이브러리만으로 connect/read 타임아웃, 기본적인 커넥션 재사용까지 다 되니, 지금 이 프로젝트 규모에는 오버엔지니어링 없이 딱 맞는 선택.
  - Apache HttpClient5: "카카오 API용 풀은 최대 20개 커넥션, 결제 PG사용 풀은 최대 5개"처럼 호출 대상(route)별로 풀 크기를 다르게 튜닝해야 하거나, 일시적 실패에 대한 재시도 정책을 표준화하고 싶거나, 모든 외부 호출에 로깅/인증 헤더를 인터셉터로 일괄 주입하고 싶을 때
  - Jetty Client: 이미 Jetty 생태계에 있을 때 선택지. 이 프로젝트처럼 Tomcat 임베디드(`spring-boot-starter-webmvc` 기본값)를 쓰는 곳에 Jetty 클라이언트를 끼워 넣으면 스레드풀/IO 엔진이 겹쳐서 오히려 관리 포인트만 늘어남. 서버 자체를 Jetty로 띄우거나 WebFlux 기반 리액티브 스택으로 갈 때 자연스럽게 따라오는 선택지

## decimal 처리 방식
DDL 생성할 때 decimal(11, 8)은 전체 11자리에서 소수점 이하 자리가 8 자리라는 것.
정수 자리수를 넘기면 overflow가 남
소수점 자리수가 넘으면 반올림 해줌. 이때 메모리상의 값과 저장 후 DB에서 다시 읽어온 값이 다를 수 있음. 따라서 `new BigDecimal(roadAddress.y()).setScale(8, RoundingMode.HALF_UP)`으로 파싱하는 시점에 명시적으로 스케일을 맞춰주는 것이 안전함
