## 메시지 큐(Kafka)
### 메시지 큐 안 쓰면?
```java
public void createOrder(Order order) {
    orderRepository.save(order);
    inventoryService.decreaseStock(order);   // 동기 호출
    paymentService.charge(order);             // 동기 호출
    emailService.sendConfirmation(order);     // 동기 호출
    shippingService.register(order);          // 동기 호출
    recommendationService.update(order);      // 동기 호출
}
```
- 사용자는 5개 서비스가 전부 끝날 때까지 기다려야 함.
- 갑자기 주문이 몰리면 5개 서비스가 동시에 부하 받고, 그중 하나라도 못 버티면 전체가 터짐

또한 DB에 테이블 따로 만들고 폴링으로 주기적으로 조회 처리 상태 변경 해야하는데 그만큼 지연과 부하가 발생하고 락 로직도 짜야 함

### 핵심 개념
- Producer: 메시지(이벤트)를 발행하는 쪽
- Topic: 메시지가 쌓이는 논리적 채널 (예: order-created)
- Partition: 토픽을 병렬 처리하기 위해 나눈 조각. 파티션 수만큼 병렬 소비가 가능
- Consumer Group: 같은 토픽을 구독하는 소비자 묶음. 그룹이 다르면 서로 독립적으로 전체 메시지를 다 받고, 그룹이 같으면 파티션을 나눠 가짐(부하 분산)
- Offset: Consumer가 어디까지 읽었는지 기록하는 위치값. Consumer가 죽어도 재시작하면 이 offset부터 이어서 읽음

 ### 이거 왜 쓰는데
 1. 주문 서비스는 "주문이 생성됐다"는 사실만 알리고, 그 이벤트를 누가 구독하는지 신경 쓸 필요가 없으니 나중에 "알림톡 서비스"를 새로 추가해도 주문 서비스 코드 수정하지 않아도 됨
 2. Buffering / 트래픽 평탄화: 순간적으로 초당 10,000건 주문이 몰려도, Kafka에 일단 쌓아두고 컨슈머는 자기 처리 속도(초당 1,000건)에 맞춰 천천히 소비하면 됨. 뒷단 DB가 폭주하지 않음
 3. 장애 격리: 이메일 서비스가 30분 다운돼도 메시지는 토픽에 그대로 쌓여 있다가, 서비스가 복구되면 이어서 처리함
 4. 재처리 가능: 로그 기반이라 offset을 되돌리면 과거 이벤트를 다시 읽을 수 있음
 5. 높은 처리량: 디스크에 순차 쓰기(append-only log) 방식이라 초당 수백만 건 처리가 가능

## Redis
### 핵심 개념
인메모리 key-value 저장소
- Publisher (발행자)
  - 특정 채널에 메시지를 발행(전송)하는 주체
  - PUBLISH channel message 명령어 사용
- Subscriber (구독자)
  - 특정 채널을 구독하고 메시지를 수신하는 주체
  - SUBSCRIBE channel 명령어 사용
- Channel (채널)
  - 메시지가 전달되는 통로. 문자열로 이름 지정 (예: news, chat-room-1)
 
### 동작 흐름
Publisher → PUBLISH "news" "속보입니다" → Redis → [Subscriber A (SUBSCRIBE "news") 수신, Subscriber B (SUBSCRIBE "news") 수신]

여러 구독자가 같은 채널을 구독하고 있으면, 발행된 메시지는 모든 구독자에게 브로드캐스트로 동시에 전달

1. DB에서 조회해서 쓰면 너무 느림
2. hashmap으로 관리할 수 있지만 서버 인스턴스 여러개면 정합성이 깨지고 서버 재시작하면 다 날라감
