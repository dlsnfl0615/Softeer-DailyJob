# HikariCP (히카리 커넥션 풀)이란?

HikariCP는 **가장 빠르고 가벼운 JDBC 커넥션 풀 라이브러리**입니다. Spring Boot 2.0부터 기본 커넥션 풀로 채택되어, 별도 설정 없이도 자동으로 사용됩니다.

## 왜 커넥션 풀이 필요한가

DB 연결(Connection)을 매번 새로 맺고 끊는 건 굉장히 비싼 작업입니다 (TCP 핸드셰이크, 인증, 세션 초기화 등). 그래서:

1. 앱 시작 시 커넥션을 미리 여러 개 만들어 **풀(Pool)**에 저장
2. 쿼리가 필요할 때 풀에서 커넥션을 **빌려서** 사용
3. 사용 후 끊지 않고 풀에 **반납**해서 재사용

이 방식으로 매번 연결/해제하는 오버헤드를 없앱니다.

## 핵심 동작 원리

```
[애플리케이션] --getConnection()--> [HikariCP Pool] --실제 연결--> [DB]
       ↑                                  |
       └──────── close() (반납) ──────────┘
```

- `close()`를 호출해도 실제로 DB 연결이 끊기는 게 아니라, **풀에 반납**되는 것뿐입니다 (프록시 객체로 가로챔).
- 풀 안의 커넥션은 Active(사용 중) / Idle(대기 중) 상태를 오가며 재사용됩니다.

## 주요 설정 항목 (Spring Boot `application.yml` 기준)

```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # 풀 최대 크기 (기본 10)
      minimum-idle: 10              # 최소 유지할 idle 커넥션 수
      connection-timeout: 30000     # 커넥션 못 받으면 대기할 최대 시간(ms), 기본 30초
      idle-timeout: 600000          # idle 커넥션 제거 전 대기 시간(ms), 기본 10분
      max-lifetime: 1800000         # 커넥션 최대 수명(ms), 기본 30분
      pool-name: MyHikariPool
```

| 옵션 | 의미 |
|---|---|
| `maximum-pool-size` | 풀이 가질 수 있는 커넥션 최대 개수 |
| `minimum-idle` | 풀이 줄어들 수 있는 최소 idle 개수 (보통 max와 동일하게 두는 걸 권장) |
| `connection-timeout` | 커넥션 대기(Pending) 시 이 시간 넘으면 예외 발생 |
| `idle-timeout` | 오래 놀고 있는 커넥션을 정리하는 주기 |
| `max-lifetime` | 커넥션이 아무리 멀쩡해도 이 시간 지나면 강제 폐기 후 재생성 (DB 측 타임아웃보다 짧게 설정 권장) |

## HikariCP가 빠른 이유

- **FastList**: ArrayList를 최적화해서 커넥션 반납 시 탐색 속도 개선
- **바이트코드 레벨 최적화**: 프록시 생성 시 불필요한 오버헤드 제거
- **락(lock) 경쟁 최소화**: 멀티스레드 환경에서 동시성 처리 효율화

## 실무에서 자주 겪는 문제

- **Pool Exhaustion**: `maximum-pool-size`보다 많은 요청이 몰리면 나머지는 Pending 상태로 대기하다가 `connection-timeout`을 넘기면 `SQLTransientConnectionException` 발생
- **Connection Leak**: 코드에서 커넥션을 반납(`close()`)하지 않고 놓치면 Active 상태로 계속 남아 풀이 서서히 고갈됨 → HikariCP는 `leakDetectionThreshold` 설정으로 이런 누수를 로그로 감지 가능

```yaml
spring:
  datasource:
    hikari:
      leak-detection-threshold: 60000   # 60초 이상 반납 안 되면 경고 로그
```

Spring Boot 프로젝트에서 실제 HikariCP 설정 값을 튜닝하는 방법이나, 방금 전 Grafana 지표(Pending=10)와 연결해서 원인 분석하는 것도 도와드릴까요?

## 로그인 부하 테스트 내가 하면 안 터지는 이유
확실히 눈에 띄는 게 하나 있어 — **로그인 하나에 평균 4.37초**, threshold(p95<1000ms)를 4.68배나 초과했어. 아까 본 `dreami-deliveries-list.js`(인덱스 없는 쿼리)보다도 훨씬 심각한 수준이야.

**숫자로 확인:**
- `http_req_duration avg=4.37s` ≈ `iteration_duration avg=4.37s` — iteration이 로그인 요청 1개뿐이니 당연히 거의 같음.
- 처리량 `4.55 req/s` ≈ `VUS(20) / avg_latency(4.37s) ≈ 4.58 req/s` — 정확히 맞아떨어져. 이건 "대기열에 걸려서 느려진 것"이 아니라 **요청 하나하나가 실제로 4초 넘게 걸리고 있다**는 뜻이야(지난번 ORDERS 쿼리 분석 때랑 같은 패턴).
- 에러는 0% — 안 터지긴 하는데 그냥 느린 거.

**왜 이렇게 느릴까 — 유력한 원인은 CPU 부족**

`PasswordHasher`가 PBKDF2WithHmacSHA256을 210,000번 반복하는 건 원래 "일부러 느리게" 설계된 거야(보안 목적 — 브루트포스 방어). 이게 원래도 요청 하나당 순수 CPU 연산으로 수십~백몇십 ms 정도는 먹는 게 정상인데, **20개가 동시에 몰리니까 4초씩 걸린다**는 건 CPU 코어 수가 20개 동시 연산을 감당 못 해서 서로 순서를 기다리며 밀리고 있다는 신호로 보여. 만약 이 EC2가 vCPU 1~2개짜리 작은 인스턴스라면, PBKDF2처럼 CPU를 꽉 채워 쓰는 연산 20개가 코어 1~2개를 나눠 쓰느라 대기시간이 눈덩이처럼 불어났을 수 있어.

**추가로 의심되는 것: t2/t3 같은 버스터블 인스턴스라면 CPU 크레딧 고갈**
버스터블 인스턴스는 평소엔 크레딧으로 순간적으로 빠르지만, CPU를 오래 꽉 채워 쓰면 크레딧이 바닥나서 베이스라인 성능으로 스로틀링돼. 6분 내내 20개 VU가 CPU 집약적인 연산을 돌렸으니, 테스트 초반보다 후반에 더 느려졌을 가능성이 있어.

**확인해보면 좋을 것들:**
1. `nproc` 또는 `lscpu`로 이 EC2의 실제 vCPU 개수 확인.
2. 인스턴스 타입 확인(t2/t3 계열이면 CPU 크레딧 관련, `CPUCreditBalance` CloudWatch 지표나 `cat /sys/fs/cgroup/cpu/cpu.stat` 등으로 스로틀링 여부 체크).
3. **`-e VUS=1`로 재실행**해서 "경합 없는 순수 1건당 비용"을 먼저 재보기 — 이게 예를 들어 150ms인데 VUS=20에서 4.37초가 나온 거면, 거의 30배 가까이 늘어난 거라 CPU 경합이 확실해짐. 반대로 VUS=1도 이미 몇 초씩 걸리면 PBKDF2 반복 횟수 자체나 다른 원인(예: 알고리즘 구현 이슈)을 의심해야 함.
4. VUS를 vCPU 개수만큼(예: 2)으로 낮춰서 돌려보고, 그때는 threshold를 통과하는지 확인 — 통과하면 "이 서버는 로그인 관점에서 동시 사용자 2명까지가 한계"라는 구체적인 용량 수치를 얻을 수 있어.
5. 테스트 도중 EC2에서 `top`이나 `vmstat 1`을 같이 띄워서 CPU 사용률이 100%에 붙어있는지 직접 관찰.

**정리하면**: 이건 코드 버그라기보단 "PBKDF2의 의도된 CPU 비용 × 이 서버의 제한된 CPU 자원"이 만나서 생긴 **용량 한계**로 보여. 실제 서비스에서 로그인이 순간적으로 몰리는 상황(예: 아침 출근 시간대)이 있다면, 지금 인프라로는 동시 로그인 20건도 버거울 수 있다는 걸 보여주는 유의미한 결과야.

## MySQL Optimizer
## MySQL 옵티마이저(Optimizer)란

같은 SQL 쿼리라도 그걸 **실제로 어떻게 실행할지**는 여러 방법(경로)이 있을 수 있어요. 옵티마이저는 이 중에서 **가장 비용이 적게 들 것 같은 방법을 선택**하는 MySQL의 내부 컴포넌트입니다.

## 왜 필요한가

```sql
SELECT * FROM orders 
WHERE customer_id = 100 AND status = 'PENDING'
ORDER BY created_at DESC;
```

이 쿼리를 실행하는 방법은 여러 가지가 있을 수 있어요:

1. **풀 테이블 스캔**: 전체 테이블을 처음부터 끝까지 훑으면서 조건에 맞는 행 찾기
2. **`customer_id` 인덱스 사용**: 인덱스로 customer_id=100인 행들만 찾은 후, 그 중에서 status 필터링
3. **`status` 인덱스 사용**: 인덱스로 status='PENDING'인 행들만 찾은 후, customer_id 필터링
4. **`(customer_id, status)` 복합 인덱스 사용**: 두 조건을 인덱스에서 한번에 걸러냄
5. **`created_at` 인덱스로 정렬 회피**: ORDER BY까지 고려해서 다른 경로 선택

옵티마이저는 이 후보들 중 하나를 **자동으로** 골라서 실행합니다. 개발자가 "이 인덱스 써!"라고 매번 지정하지 않아도 되는 이유가 이것 때문이에요.

## 어떻게 고르나 (Cost-Based Optimizer)

MySQL(InnoDB)은 **비용 기반 최적화**를 씁니다. 대략 이런 정보를 참고해요:

- **테이블 통계 정보**: 행 수, 각 컬럼의 카디널리티(고유값 개수) — `ANALYZE TABLE`로 갱신
- **인덱스 선택도(selectivity)**: 이 조건으로 걸러지면 몇 행이나 남을지 예측
- **예상 I/O 비용**: 디스크(또는 버퍼풀) 접근 횟수 추정
- **정렬/임시테이블 필요 여부**: filesort, temporary table 사용 여부도 비용에 포함

이 예측치들을 종합해서 **"비용 점수"**를 계산하고, 가장 낮은 후보를 선택합니다.

## 실전에서 확인하는 법

```sql
EXPLAIN SELECT * FROM orders 
WHERE customer_id = 100 AND status = 'PENDING'
ORDER BY created_at DESC;
```

`EXPLAIN` 결과에서 확인할 핵심 컬럼:

| 컬럼 | 의미 |
|---|---|
| `type` | 접근 방식 (ALL=풀스캔, ref/range=인덱스 사용, const 등) |
| `key` | 실제로 선택된 인덱스 |
| `rows` | 예상 스캔 행 수 |
| `Extra` | Using filesort, Using temporary 등 추가 비용 발생 여부 |

## 옵티마이저가 "잘못" 고르는 경우

통계 정보가 오래됐거나, 데이터 분포가 예측과 다르면 옵티마이저가 최선이 아닌 인덱스를 고를 수 있어요. 이럴 때 대응법:

```sql
-- 통계 갱신
ANALYZE TABLE orders;

-- 강제로 특정 인덱스 쓰게 하기 (최후의 수단)
SELECT * FROM orders USE INDEX (idx_customer_status) 
WHERE customer_id = 100 AND status = 'PENDING';

-- 특정 인덱스 못 쓰게 막기
SELECT * FROM orders IGNORE INDEX (idx_created_at) ...
```

## 정리

옵티마이저는 사람이 매번 "이 쿼리는 이 인덱스로 실행해"라고 지정하지 않아도, **통계 기반으로 여러 실행 후보 중 가장 효율적일 것 같은 경로를 자동으로 선택**해주는 역할을 합니다. 다만 이 예측이 항상 완벽하진 않으니, 성능이 이상하면 `EXPLAIN`으로 실제 선택된 경로를 확인하는 습관이 중요해요.
