## HikariCP (히카리 커넥션 풀)
HikariCP는 가장 빠르고 가벼운 JDBC 커넥션 풀 라이브러리임. Spring Boot 2.0부터 기본 커넥션 풀로 채택되어 별도 설정 없이도 자동 사용됨.

### 커넥션 풀이 필요한 이유
DB 연결을 매번 새로 맺고 끊는 것은 비용이 큰 작업임(TCP 핸드셰이크, 인증, 세션 초기화 등). 그래서 다음과 같이 동작함.
1. 앱 시작 시 커넥션을 미리 여러 개 만들어 풀(Pool)에 저장
2. 쿼리가 필요할 때 풀에서 커넥션을 빌려서 사용
3. 사용 후 끊지 않고 풀에 반납해서 재사용

이 방식으로 매번 연결/해제하는 오버헤드를 제거함.

### 핵심 동작 원리
```
[애플리케이션] --getConnection()--> [HikariCP Pool] --실제 연결--> [DB]
       ↑                                  |
       └──────── close() (반납) ──────────┘
```
- `close()` 호출 시 실제 DB 연결이 끊기는 것이 아니라 풀에 반납되는 것뿐임(프록시 객체로 가로챔).
- 풀 안의 커넥션은 Active(사용 중)/Idle(대기 중) 상태를 오가며 재사용됨.

### 주요 설정 항목 (Spring Boot `application.yml` 기준)
```yaml
spring:
  datasource:
    hikari:
      maximum-pool-size: 10        # 풀 최대 크기 (기본 10)
      minimum-idle: 10              # 최소 유지할 idle 커넥션 수
      connection-timeout: 30000     # 커넥션 못 받으면 대기할 최대 시간(ms), 기본 30초
      idle-timeout: 600000          # idle 커넥션 제거 전 대기 시간(ms), 기본 10분
      max-lifetime: 1800000         # 커넥션 최대 수명(ms), 기본 30분
      pool-name: MyHikariPool
```

| 옵션 | 의미 |
|---|---|
| `maximum-pool-size` | 풀이 가질 수 있는 커넥션 최대 개수 |
| `minimum-idle` | 풀이 줄어들 수 있는 최소 idle 개수 (보통 max와 동일하게 두는 것을 권장) |
| `connection-timeout` | 커넥션 대기(Pending) 시 이 시간 초과 시 예외 발생 |
| `idle-timeout` | 오래 놀고 있는 커넥션을 정리하는 주기 |
| `max-lifetime` | 커넥션이 정상이어도 이 시간 경과 시 강제 폐기 후 재생성 (DB 측 타임아웃보다 짧게 설정 권장) |

### HikariCP가 빠른 이유
- FastList: ArrayList를 최적화해 커넥션 반납 시 탐색 속도 개선
- 바이트코드 레벨 최적화: 프록시 생성 시 불필요한 오버헤드 제거
- 락(lock) 경쟁 최소화: 멀티스레드 환경에서 동시성 처리 효율화

### 실무에서 자주 겪는 문제
- Pool Exhaustion: `maximum-pool-size`보다 많은 요청이 몰리면 나머지는 Pending 상태로 대기하다 `connection-timeout` 초과 시 `SQLTransientConnectionException` 발생
- Connection Leak: 코드에서 커넥션 반납(`close()`)을 누락하면 Active 상태로 계속 남아 풀이 서서히 고갈됨 → `leakDetectionThreshold` 설정으로 누수 감지 가능

```yaml
spring:
  datasource:
    hikari:
      leak-detection-threshold: 60000   # 60초 이상 반납 안 되면 경고 로그
```

## 로그인 부하테스트 시 서버가 터지지 않는 이유
로그인 하나당 평균 4.37초 소요, threshold(p95<1000ms) 대비 4.68배 초과. 이전에 확인한 `dreami-deliveries-list.js`(인덱스 없는 쿼리)보다도 심각한 수준임.

### 수치 확인
- `http_req_duration avg=4.37s` ≈ `iteration_duration avg=4.37s` — iteration이 로그인 요청 1개뿐이라 거의 동일.
- 처리량 `4.55 req/s` ≈ `VUS(20) / avg_latency(4.37s) ≈ 4.58 req/s` — 대기열 지연이 아니라 요청 하나하나가 실제로 4초 이상 소요됨을 의미(이전 ORDERS 쿼리 분석과 동일한 패턴).
- 에러율 0% — 실패하지 않고 단순히 느림.

### 유력한 원인 — CPU 자원 부족
`PasswordHasher`가 PBKDF2WithHmacSHA256을 210,000번 반복하는 것은 보안 목적(브루트포스 방어)으로 의도적으로 느리게 설계된 연산임. 요청 하나당 순수 CPU 연산으로 수십~백몇십 ms가 정상 범위인데, 20개가 동시에 몰려 4초씩 걸리는 것은 CPU 코어 수가 20개 동시 연산을 감당하지 못해 대기가 발생하고 있다는 신호로 판단됨. vCPU 1~2개 규모의 인스턴스라면 PBKDF2처럼 CPU를 많이 쓰는 연산 20개가 코어 1~2개를 나눠 쓰며 대기시간이 누적됐을 가능성이 있음.

### 추가 의심 요인 — 버스터블 인스턴스의 CPU 크레딧 고갈
t2/t3 계열 버스터블 인스턴스는 평소 크레딧으로 순간적으로 빠르게 동작하나, CPU를 오래 꽉 채워 쓰면 크레딧이 소진되어 베이스라인 성능으로 스로틀링됨. 6분간 20개 VU가 CPU 집약적 연산을 지속했으므로, 테스트 후반으로 갈수록 더 느려졌을 가능성 있음.

### 확인이 필요한 항목
1. `nproc` 또는 `lscpu`로 EC2의 실제 vCPU 개수 확인
2. 인스턴스 타입 확인(t2/t3 계열이면 `CPUCreditBalance` CloudWatch 지표나 `cat /sys/fs/cgroup/cpu/cpu.stat` 등으로 스로틀링 여부 확인)
3. `-e VUS=1`로 재실행해 경합 없는 순수 1건당 비용 측정 — 예를 들어 150ms인데 VUS=20에서 4.37초가 나왔다면 약 30배 증가로 CPU 경합이 확실해짐. 반대로 VUS=1도 이미 수 초가 걸리면 PBKDF2 반복 횟수 자체나 다른 구현 이슈를 의심해야 함
4. VUS를 vCPU 개수 수준(예: 2)으로 낮춰 재실행 후 threshold 통과 여부 확인 — 통과 시 "이 서버는 로그인 관점에서 동시 사용자 2명까지가 한계"라는 구체적 용량 수치 확보 가능
5. 테스트 중 EC2에서 `top` 또는 `vmstat 1`로 CPU 사용률이 100%에 근접하는지 직접 관찰

정리: 코드 버그가 아니라 PBKDF2의 의도된 CPU 비용과 서버의 제한된 CPU 자원이 결합된 용량 한계로 판단됨. 로그인이 순간적으로 몰리는 상황(예: 출근 시간대)에서는 현재 인프라 기준 동시 로그인 20건도 부담될 수 있음을 보여주는 결과임.

## MySQL 옵티마이저(Optimizer)

같은 SQL 쿼리라도 실제 실행 방법(경로)은 여러 가지가 있을 수 있음. 옵티마이저는 이 중 비용이 가장 적게 드는 방법을 선택하는 MySQL의 내부 컴포넌트임.

### 옵티마이저가 필요한 이유
```sql
SELECT * FROM orders 
WHERE customer_id = 100 AND status = 'PENDING'
ORDER BY created_at DESC;
```
이 쿼리를 실행하는 방법은 여러 가지임.
1. 풀 테이블 스캔: 전체 테이블을 훑으며 조건에 맞는 행 탐색
2. `customer_id` 인덱스 사용: 인덱스로 customer_id=100인 행을 찾은 후 status 필터링
3. `status` 인덱스 사용: 인덱스로 status='PENDING'인 행을 찾은 후 customer_id 필터링
4. `(customer_id, status)` 복합 인덱스 사용: 두 조건을 인덱스에서 한 번에 필터링
5. `created_at` 인덱스로 정렬 회피: ORDER BY까지 고려한 경로 선택

옵티마이저는 이 후보들 중 하나를 자동으로 선택함. 개발자가 매번 인덱스를 지정하지 않아도 되는 이유임.

### 선택 방식 (Cost-Based Optimizer)
MySQL(InnoDB)은 비용 기반 최적화를 사용함. 참고하는 정보는 다음과 같음.
- 테이블 통계 정보: 행 수, 각 컬럼의 카디널리티(고유값 개수) — `ANALYZE TABLE`로 갱신
- 인덱스 선택도(selectivity): 조건 적용 시 남는 행 수 예측
- 예상 I/O 비용: 디스크(또는 버퍼풀) 접근 횟수 추정
- 정렬/임시테이블 필요 여부: filesort, temporary table 사용 여부도 비용에 포함

이 예측치를 종합해 비용 점수를 계산하고, 가장 낮은 후보를 선택함.

### 확인 방법
```sql
EXPLAIN SELECT * FROM orders 
WHERE customer_id = 100 AND status = 'PENDING'
ORDER BY created_at DESC;
```
`EXPLAIN` 결과에서 확인할 핵심 컬럼은 다음과 같음.

| 컬럼 | 의미 |
|---|---|
| `type` | 접근 방식 (ALL=풀스캔, ref/range=인덱스 사용, const 등) |
| `key` | 실제로 선택된 인덱스 |
| `rows` | 예상 스캔 행 수 |
| `Extra` | Using filesort, Using temporary 등 추가 비용 발생 여부 |

### 옵티마이저가 잘못 고르는 경우
통계 정보가 오래됐거나 데이터 분포가 예측과 다르면 옵티마이저가 최선이 아닌 인덱스를 선택할 수 있음. 대응 방법은 다음과 같음.
```sql
-- 통계 갱신
ANALYZE TABLE orders;

-- 강제로 특정 인덱스 사용 (최후의 수단)
SELECT * FROM orders USE INDEX (idx_customer_status) 
WHERE customer_id = 100 AND status = 'PENDING';

-- 특정 인덱스 사용 차단
SELECT * FROM orders IGNORE INDEX (idx_created_at) ...
```

## 부하테스트

### 20개 계정에 각각 5000건씩 적재, 동시 요청 20개 테스트
5000건씩 실제로 적재된 상태에서 테스트가 진행됨.

데이터가 실제로 존재했음을 확인: `http_reqs(17060) - 로그인(20) = 17040`을 `iterations(568)`로 나누면 `17040/568 = 정확히 30.0` — 모든 iteration이 `MAX_PAGES=30`을 채웠음. 계정당 5000건(size=20 기준 250페이지) 존재하므로 30페이지 캡에 걸려 종료된 것이며, 데이터 부족으로 조기 종료된 것이 아님. 이전 두 차례의 "1건에서 끝남" 문제가 이번에는 해결됨.

핵심 결과: threshold는 통과함(p95=363ms < 500ms). `{name:deliveries}` avg=346.79ms, median=347.68ms, p95=363.16ms.

이전에 dreami1 계정 하나로 세션 하나를 공유해 돌렸던 테스트(avg=307ms, p95=353ms)와 비교하면 거의 동일한 수치임. 다계정 테스트를 만든 목적은 "지연이 쿼리 비용 때문인지, 세션 하나를 공유해 서버가 내부적으로 직렬화한 것 때문인지" 구분하기 위함이었음. 세션을 20개로 완전히 분리했는데도 동일하게 약 350ms가 나온 것은, 세션 공유/직렬화가 원인이 아니었음을 확인해줌. 순수하게 쿼리 자체(인덱스 없는 풀스캔)가 병목이라는 결론이 서로 다른 두 설계의 테스트에서 일관되게 나타남.

동시성 계산도 부합함: 처리량 `56.02 req/s` ≈ `VUS(20) / avg_latency(0.35s) ≈ 57.1 req/s` — 대기열 지연이 아니라 요청 하나하나가 실제로 350ms씩 소요됨을 의미(이전 분석과 동일한 패턴).

`p95<500ms` threshold 통과가 "빠르다"는 의미는 아님. 단순 페이지네이션 쿼리(21건 조회)는 인덱스만 있으면 한 자릿수~수십 ms면 처리되는 것이 정상임. 현재 350ms는 기존에 설정한 여유로운 기준선(500ms)은 통과하지만, 인덱스가 있었을 경우 대비 여전히 느린 수치임.

정리: 이번 결과로 ORDERS 테이블 인덱스 부재가 세션 공유 여부와 무관한 실제 병목이라는 점이 재확인됨. 다음 단계로 실제 인덱스(`idx_orders_dreami_dtm` 등)를 적용한 뒤 동일 조건(20계정×5000건, VUS=20)으로 재실행해 p95 하락폭을 비교하는 것이 자연스러운 후속 작업임.
