# 오늘 한 일

## 세션 1개에 대한 SSE 처리 방식 비교

### 1. 세션 1개 + SSE 1개 (서버가 강제로 1개만 유지)
새 연결 발생 시 서버가 기존 연결을 끊고 교체하는 방식임.
- 구조: 세션당 커넥션 1개만 유지 (`Map<SessionId, SseEmitter>`)
- 장점: 서버 구현이 단순, 리소스 사용량 예측 용이
- 단점: 탭을 여러 개 열면 나중에 연 탭만 살아남고 이전 탭은 알림 끊김, 사용자 혼란 유발 가능
- 적합한 경우: 멀티탭을 고려하지 않아도 되는 서비스, 혹은 "기기당 1회만 알림"이 정책상 요구되는 경우

### 2. 세션 1개 + SSE 여러 개 (서버가 다중 연결 허용)
같은 세션에서 여러 탭이 각자 SSE를 열고, 서버가 목록을 관리하며 전체에 브로드캐스트하는 방식임.
- 구조: 세션당 커넥션 목록 유지 (`Map<SessionId, List<SseEmitter>>`)
- 장점: 탭 개수와 무관하게 모든 탭에서 알림 수신, 클라이언트 처리 불필요
- 단점: 세션당 연결 수 증가에 따른 서버 리소스 부담 증가, 상한선 설정 필요
- 적합한 경우: 일반적인 실시간 알림/채팅/대시보드 서비스 (가장 널리 쓰이는 방식)

#### 연결 불안정이 함께 언급되는 이유
EventSource는 네트워크 문제로 연결이 끊기면 브라우저가 자동으로 재연결을 시도함. 이 과정에서 이전 연결이 서버에서 완전히 정리되기 전에 새 연결 요청이 먼저 도착하는 타이밍 이슈 발생 가능. 이때 서버가 "세션당 SSE 1개"를 엄격히 강제할 경우, 순간적인 중복을 규칙 위반으로 처리해 불필요한 충돌 처리 로직이 필요해짐. 다중 연결 허용 시 재연결 시 순간적인 겹침도 자연스럽게 넘어갈 수 있으나, 이는 다중 허용 정책의 원인이 아니라 그로 인한 부수적 이점임.

### 3. 브로드캐스트 채널 방식 (서버는 1개, 클라이언트가 탭 간 공유)
서버는 세션당 SSE를 1개만 열고, 브라우저 탭 중 리더 하나만 실제 연결을 담당해 `BroadcastChannel`이나 `SharedWorker`로 다른 탭에 데이터를 전파하는 방식임.
- 구조: 서버는 방식 1과 동일(세션당 1개), 클라이언트에 리더 선출 로직 추가
- 장점: 서버 부담은 방식 1 수준, 사용자 경험은 방식 2 수준
- 단점: 클라이언트 구현 복잡도 증가(리더 선출, 리더 다운 감지, 재연결 로직), 브라우저 호환성 고려 필요(SharedWorker의 Safari 이슈)
- 적합한 경우: 서버 커넥션 수 최소화와 멀티탭 UX를 동시에 챙겨야 하는 서비스

### 비교

| 항목 | 1. SSE 1개 강제 | 2. SSE 여러개 허용 | 3. 브로드캐스트 공유 |
|---|---|---|---|
| 서버 커넥션 수 | 세션당 1개 | 세션당 N개(탭 수만큼) | 세션당 1개 |
| 멀티탭 알림 수신 | 마지막 탭만 됨 | 모든 탭에서 됨 | 모든 탭에서 됨 |
| 서버 구현 복잡도 | 낮음 | 중간(상한선 관리) | 낮음 |
| 클라이언트 구현 복잡도 | 낮음 | 낮음 | 높음(리더 선출 필요) |
| 서버 리소스 효율 | 좋음 | 탭 많으면 나쁨 | 좋음 |

정리: 트래픽/리소스 부담이 적은 서비스는 방식 2로 충분하고, 동시 접속자가 많거나 서버 커넥션 비용이 부담되는 서비스는 클라이언트 복잡도를 감수하고 방식 3을 고려하는 것이 합리적임.

## K6 로그인 부하테스트 시 세션 누적 여부
`login.js`는 시드된 부르미(boormi1, boormi2)와 드리미(dreami1~10) 12개 계정으로 `POST /api/v1/user/login`을 실제 호출함. mock 없이 진짜 `PasswordHasher` 검증과 진짜 `HttpSession` 발급을 거침.

로그아웃 없음. 스크립트 주석에도 "세션 정리는 안 함"이라고 명시됨. 로그인 한 번만 수행하고 종료, 로그아웃 API 호출 코드는 어디에도 없음.

세션이 무한정 쌓이지는 않음 — k6는 VU마다 쿠키를 자동 유지해, 같은 VU가 반복(iteration)할 때마다 직전 로그인의 `JSESSIONID` 쿠키를 재전송함. `LoginSession.create()`가 세션 고정(fixation) 방어를 위해 "요청에 실려온 기존 세션을 무효화하고 새 세션 발급"하는 구조라, 같은 VU 안에서는 로그인마다 직전 세션이 자동 무효화되고 새 세션으로 교체됨. 따라서 동시에 살아있는 세션 수는 최대 `VUS`개 수준이며, 반복 횟수만큼 누적되지 않음.

SSE는 관여하지 않음. 스크립트는 `EventSource`/SSE 연결을 열지 않음 — SSE는 프론트엔드(`MatchingPopup`, `DeliveryTrackScreen` 등)가 브라우저에서 여는 것이라, 순수 백엔드 API만 호출하는 이 스크립트 관점에서는 해제할 SSE 연결이 없음. 로그아웃 시 서버가 해당 사용자의 SSE emitter를 정리하는 로직이 있어도, 로그아웃 자체를 수행하지 않으므로 해당 경로는 실행되지 않음.

## 부하테스트로 느린 쿼리 찾기
요청 단위로 느린 지점을 먼저 찾고, 그 요청 안에서 실제 문제 쿼리를 좁히는 2단계 흐름임.

### 1단계 — 어느 엔드포인트가 느려지는지 확인
PLAN.md ①③번이 이 목적(카카오 의존 없는 순수 조회)으로 설계됨.
```bash
k6 run -e VUS=10 -e DURATION=1m loadtest/k6/boormi-calls-list.js
k6 run -e VUS=50 -e DURATION=1m loadtest/k6/boormi-calls-list.js
```
VUS를 10→50→100으로 단계적으로 올리며 `http_req_duration`의 p95/p99 확인. VUS 증가에 따라 비선형적으로 급격히 느려지는 엔드포인트는 쿼리 문제일 가능성이 높음(단순 CPU 병목은 보통 완만하게 나빠짐).

또 다른 확인 축은 ③번 취지대로 데이터량을 SQL로 늘려가며 같은 VUS로 재실행하는 것임. VUS는 고정한 채 데이터가 늘수록 느려진다면 동시성 문제가 아니라 인덱스 없는 풀스캔/N+1처럼 데이터량에 비례해 나빠지는 쿼리라는 신호임.

### 2단계 — 그 요청 안의 실제 쿼리 확인
느려진 엔드포인트가 특정되면, 부하테스트를 짧게 재실행하며 쿼리 레벨 확인.
- Hibernate SQL 로깅 활성화(`application.properties`의 `spring.jpa.show-sql`을 테스트 동안만 `true`로, 또는 `logging.level.org.hibernate.SQL=DEBUG`) — 요청 하나당 쿼리 발생 횟수 확인 가능. 같은 모양의 쿼리가 결과 건수만큼 반복되면 N+1임. PLAN.md ①번에 기재된 패턴이 정확히 이 경우로, `NearbyOrderFinder.find()` → `DreamiService.toNearbyCallDto()`가 결과 건수만큼 `orderRepository.findById()`를 개별 호출함(코드 리딩으로 이미 확인된 케이스). `hibernate.default_batch_fetch_size=100`이 설정돼 있으나 지연로딩 연관관계에만 적용되므로 이런 명시적 반복 호출 코드는 해당 없음.
- MySQL 슬로우 쿼리 로그 — 부하테스트 동안만 활성화.
  ```sql
  SET GLOBAL slow_query_log = 1;
  SET GLOBAL long_query_time = 0.1;  -- 100ms 넘는 쿼리만
  ```
  종료 후 `mysqldumpslow -s t /var/log/mysql/slow.log`(또는 `pt-query-digest`)로 누적 시간/호출 횟수 기준 랭킹 확인. 계속 켜두면 로그가 커지므로 테스트 구간에서만 사용.
- 의심 쿼리는 `EXPLAIN`으로 풀스캔(`type: ALL`) 여부와 인덱스 사용 여부 확인.

### 3단계 — 수정 후 재검증
인덱스 추가 또는 N+1 배치 조회로 수정 후, 동일 스크립트를 동일 VUS/데이터량으로 재실행해 p95 개선 여부 비교. 이 전/후 비교가 부하테스트로 쿼리 성능 문제를 찾았음을 증명하는 근거임.

참고: `monitoring/`에 Prometheus+Grafana 연동됨(`/actuator/prometheus`). k6 실행 중 Grafana의 `http_server_requests_seconds` 대시보드를 함께 확인하면 엔드포인트별 지연시간 추이를 실시간으로 보며 슬로우 로그 활성화 시점을 잡기 용이함.

## 로그인 API 지연 원인

반복문 존재하나, 개발자가 직접 작성한 것이 아니라 JDK 내장 암호 라이브러리 내부에서 도는 반복임. `PasswordHasher.java` 기준:
```java
private static final int ITERATIONS = 210_000;
...
PBEKeySpec spec = new PBEKeySpec(rawPassword.toCharArray(), salt, ITERATIONS, KEY_BITS);
return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
```
여기서 `210_000`은 `PBEKeySpec`의 반복 횟수 파라미터이며, 실제 HMAC-SHA256을 210,000번 체이닝하는 반복문은 JDK의 `SecretKeyFactory` 구현체 내부(자바 표준 암호 프로바이더)에 위치함. 프로젝트 코드에는 명시적 반복문이 없고, JDK에 알고리즘과 반복 횟수를 위임하는 구조임.

PBKDF2를 반복하는 이유: 비밀번호를 SHA256으로 한 번만 해시하면 연산이 너무 빨라, DB 유출 시 공격자가 초당 수십억 개의 비밀번호 후보를 대입 가능(브루트포스). PBKDF2는 연산 비용을 의도적으로 높여 대입 속도를 늦추는 알고리즘임 — HMAC-SHA256을 210,000번 체이닝(이전 라운드 출력이 다음 라운드 입력)해, 정상 로그인 1회는 체감 지연이 크지 않으나(수십~수백 ms) 대량 대입 시도에는 시간이 곱절로 소요되게 만듦.

즉 로그인 지연은 버그가 아니라 보안을 위해 의도적으로 설정된 비용임. 다만 최솟값조차 977ms로 측정된 것은 이 의도된 비용이 현재 서버 하드웨어에서 예상보다 크게 소요되고 있다는 의미이며, 반복 횟수(210,000) 하향 또는 서버 CPU 증설의 트레이드오프를 논의할 지점임.

결론: VUS=10 수준에서는 장시간 실행에도 성능 저하 없이 안정적임. 목표(500ms)와 실측(14.56ms) 격차가 30배 이상이므로, 실행 시간을 늘리기보다 동시 사용자 수(VUS)를 올려 p95가 무너지기 시작하는 지점을 확인하는 실험이 다음 단계로 유효함.

## 드리미 사진 인증 시 부르미 테이블 미수정

## DreamiService의 Order 테이블 직접 수정 - 안전장치 부재

### 1. 문제
`DreamiService.acceptOffer()`가 주문 상태 확인 없이 무조건 씀.
```java
Orders order = orderRepository.findById(orderId)...
order.markPendingBoormiConfirmation();   // MATCHING인지 확인 없이 무조건 PENDING 전이
```
- `isDreamiOfferOwner`는 "내 오퍼인가"만 확인하고, 오퍼 생존 여부(OFFERED 여부)는 미확인
- 선착순 경쟁에서 진 드리미도 수락 버튼을 눌러 이 검사를 통과 → DB 선기록 후 커밋, 매칭 엔진 제출 → 마감 사실을 뒤늦게 인지 → 되돌리는 로직 없음
- 추가로 `Orders`에 `@Version`/`@DynamicUpdate` 부재 → dirty checking이 전체 컬럼 UPDATE를 발생시켜, 늦게 커밋된(패배한) 트랜잭션이 자신의 트랜잭션 시작 시점의 낡은 스냅샷(예: `dreami_id=null`)까지 함께 덮어씀

### 2. 원인으로 발생한 문제
- 200건 중 4건(약 1%)에서, `ORDERS`가 이미 `IN_PROGRESS`로 확정된 후 나중에 커밋된 패배자 트랜잭션이 `order_cd`를 `PENDING`으로, `dreami_id`를 `null`로 되돌림(전체 컬럼 덮어쓰기) → `DELIVERY`는 이미 생성되어 있는데 `ORDERS`만 되감겨 두 테이블 불일치 발생
- 그중 1건은 되감기가 배달 시작 트랜잭션보다 먼저 발생 → 엔진이 주문 재조회 시 `IN_PROGRESS`가 아니라고 판단 → 배달 미시작(실제 서비스 장애)
- 나머지는 SSE `delivery_started` 알림 유실로 이어짐 — 별개 버그가 아니라 이 문제의 하위 증상

### 3. 해결책과 장단점

#### ① if 조건문 가드
- 장점: 구현 단순
- 단점: 확인과 쓰기 사이 시간차 존재 → 진짜 동시 통과 케이스 차단 불가, 근본 해결 아님

#### ② 낙관적 락(@Version)
- 장점: JPA 표준, 엔티티 방식 유지 가능
- 단점: 스키마 컬럼 추가 필요, 충돌이 커밋(flush) 시점에야 예외로 발현되어 예외 변환 로직 별도 필요, AFTER_COMMIT 이벤트 구조와 맞물려 복잡도 증가

#### ③ 비관적 락
- 장점: 확실한 순차 처리, 이해 용이
- 단점: 락 대기 행렬 발생, 다수 드리미 경합 시 손해 증가

#### ④ @DynamicUpdate
- 장점: 낡은 스냅샷으로 인한 타 컬럼 덮어쓰기 방지
- 단점: ③ 채택 시 dirty checking 자체가 발생하지 않아 불필요

#### ⑤ 조건부 UPDATE(WHERE order_cd='MATCHING')
- 장점: 확인+쓰기 완전 원자적, 스키마 변경 불필요, 영향행 0/1로 결과 즉시 판단 가능, 기존 네이티브 쿼리 관행과 일치
- 단점: 엔티티 미경유로 같은 트랜잭션 내 캐시된 엔티티 존재 시 stale 위험(clearAutomatically로 방어 가능하나, 현재 메서드는 캐시가 없어 해당 없음), 방어 시에도 의도치 않은 detach 문제 발생 가능

### 단순 락만 사용하는 경우
시나리오(락만 걸고 무조건 씀):
- A: 락 획득 → 값 수정(PENDING) → 락 해제(커밋)
- B: (A 종료까지 대기) → 락 획득 → 값 수정(PENDING) → 락 해제(커밋), 그대로 덮어씀

이 경우 순서만 강제될 뿐 B가 여전히 무조건 쓰기 때문에 문제 해결 안 됨. 락은 동시 진입만 차단할 뿐, 진입 후 처리는 코드가 판단해야 함.

### 락 방식 적용 시
- A: 락 획득(FOR UPDATE로 조회) → 상태 확인(MATCHING) → PENDING으로 수정 → 락 해제(커밋)
- B: (A 종료까지 대기) → 락 획득(FOR UPDATE로 조회) → 상태 확인(A가 이미 변경해 PENDING/IN_PROGRESS로 확인됨) → MATCHING 아님 판정 → 쓰지 않고 ALREADY_ACCEPTED_BY_OTHER 예외 처리

### 4. 최종 선택

①: if 조건문 가드만
확인(check)과 쓰기(write) 사이에 시간차가 남아, 두 트랜잭션이 동시에 MATCHING을 보고 둘 다 통과하는 진짜 동시성 케이스를 차단 불가. 근본 해결 아님.

②: 낙관적 락(@Version)
스키마 컬럼 추가 필요. 충돌이 커밋(flush) 시점에야 예외로 발생해 OptimisticLockException을 잡아 비즈니스 예외로 전환하는 처리가 별도 필요. 현재 구조(수락 즉시 커밋 후 AFTER_COMMIT 이벤트 발행)와 맞물려 복잡도만 증가.

③: 조건부 UPDATE(원자적 네이티브 쿼리)
원자성은 확실하고 스키마 변경도 없음. 다만 영속성 컨텍스트를 우회하는 방식이라, `markConsumedIfIssued`의 `clearAutomatically=true`가 같은 트랜잭션의 delivery 엔티티를 detach시켜 상태 변경이 유실된 사례와 같은 계열의 위험을 코드에 남김. 현재는 acceptOffer가 다른 엔티티를 건드리지 않아 안전하나, 추후 로직 추가 시 재발 가능한 숨은 전제조건임.

④: @DynamicUpdate — 탈락(불필요)
낡은 스냅샷이 타 컬럼까지 덮어쓰는 증상만 완화하는 대증요법. ③이나 ⑤ 채택 시 전체 컬럼 dirty-checking UPDATE 자체가 발생하지 않거나(③), 락 안에서 최신값을 재확인하므로(⑤) 문제가 자동 해소되어 별도 적용 불필요.

⑤: 비관적 락(@Lock(PESSIMISTIC_WRITE)) → 채택
1. 영속성 컨텍스트 우회 없음 — 엔티티를 정상 로드하고 정상적인 dirty-checking으로 flush함. ③의 "추후 재발 가능한 stale-read 위험"이 구조적으로 존재하지 않음.
2. 코드베이스에 이미 검증된 패턴 — `DreamiRepository.findByDreamiId`가 같은 목적(check-then-act 직렬화)으로 이미 사용 중. 기존 컨벤션 재사용.
3. 스키마 변경 불필요 — ②와 달리 컬럼 추가 없음.
4. 락 대기 비용이 이 시나리오에서는 무시 가능한 수준 — 실제 동시성 규모(한 주문에 최대 3명, MAX_OFFER_COUNT)와 임계구역 길이(상태 하나 바꾸는 짧은 트랜잭션)를 고려하면 대기시간은 수십~수백 밀리초 수준으로, 30초 TTL과 비교해 무시 가능.
5. 가독성 — check-then-act가 자바 코드에 그대로 드러남(`if (order.getOrderCd() != MATCHING) throw ...`). SQL WHERE절에 암묵적으로 숨어있는 ③보다 이해 용이.
